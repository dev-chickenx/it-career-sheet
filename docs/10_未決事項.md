読み方の規則。

1. **本書に仕様はない。**決まったことは仕様書にある
2. 2章は要求だけを書く。要求とは、依頼者が何を求めているかであって、どう作るかではない
3. 2章の「サンプル」は要求の輪郭を示す例である。決定ではない
4. 3章は却下の記録である。ここに載っている案を再提案しない
5. 節番号・設問数・ファイル名は本書に書かない。仕様書側で動くため、書くと本書が先に古くなる
6. 本書の中の参照も節番号で書かない。要求の名前で指す。節を並べ替えると番号がずれる

「sample の出力を見て決める」とは、prototype の sample に値を入れて動かし、その結果を見て判断することを指す。複数人から回答を集めることではない。

## 2. 未決の要求

### 2.1. ブロック2を経験の有無だけを聞くものにする

| 項目 | 内容 |
| --- | --- |
| 要求 | ブロック2は工程を担当した経験だけを聞くものにし、技術的な中身はすべてブロック3に持たせる。観点をブロック3と突き合わせて重複を判定する作業が、観点を増減させるたびに発生している。判定そのものが起きない構造にする |

工程の中で何をするかを書こうとすると技術語が出てくるため、ルールを足しても再発を止められない。関与の深さは関与型アンカーが既に測っているので、観点側に深さの語を書くと二重取りになる。

サンプル。方向は3つ。

| # | 方向 | 失うもの |
| --- | --- | --- |
| 1 | 現行維持。逸脱している観点だけを担当軸の語に直す。曖昧さの残る観点には説明文を付ける（付けるかどうかは未決） | 重複判定は今後も発生し続ける |
| 2 | 工程あたり1観点にする。深さは関与型アンカーだけで測る | 工程内の担当範囲の解像度。要件定義でヒアリングだけの人と合意形成まで持つ人が同じ値になる |
| 3 | 工程内の観点は残し、観点名を成果物と行為だけで書く | なし。ただし重複判定は残る（基準は「技術語が入っていないか」の1つになる） |

観点名で具体化する道は塞がっている。成果物名を置くと、その成果物を持たない分野の回答者の列が落ちる。判断軸を置くと能力語になり、ブロック3の領分に入る。曖昧に見える記述が、この2つを同時に満たした結果である場合がある。残る手段は説明文である。分野依存の語も、説明文の例示であれば「どれか当てはまればよい」ため列を落とさない。

順序の制約。対応可能なポジションの判定条件は工程の値を使う。先に観点数を動かすと、同じ数値を二度承認することになる。

本項の結論は、ブロック2の観点の現行内容を上書きしうる。設問のIDの付け方は、本項を決めてから着手する。

## 3. 採らなかった案

### 3.1. 対応可能なポジション

カタログの選定基準は4点。実在性・現在性（実務で現在も使われているか）、対象者適合（本シートの対象者が名乗りうるか）、重複の整理（他候補と概念が大きく重ならないか）、手法非依存（特定の開発手法の中でのみ定義されるアカウンタビリティでないか）。

| 不採用にした候補 | 理由 |
| --- | --- |
| CTO | 経営層であり、対象者に適合しない |
| SRE | 業務ジャンルの職種名に既出で重複する |
| エンジニアリングマネージャー | 公式な定義主体がなく、プロジェクトマネージャーと重複する |
| プロダクトオーナー | Scrum 固有の責務。Scrum Guide 2020版が「役割」を「アカウンタビリティ」に呼称変更しているとおりであり、手法非依存の設計と矛盾する |

| 案 | 採らない理由 |
| --- | --- |
| 「要件定義担当」「設計担当」という呼称を使う | 実務の呼称と一致しない。厚労省 job tag は要件定義から設計を「システムエンジニア」という1つの役割として扱う |

### 3.2. 打合せの要望のうち実現しなかったもの

議事録を読むと頼んだのに入っていないように見えるもの。理由を残す。

| 要望 | 実現しなかった理由 |
| --- | --- |
| 汎用能力を G1 開発・実装／G2 開発環境・プロセス／G3 コミュニケーション・マネジメント の3グループで保ち、各グループのカテゴリ数を5件に揃える | 大分類を廃止した。この層の根拠はレーダーを3枚にするという表示の都合だけで、分析にも判定にも使われていなかった。5件に揃えると、枠を埋めるためのカテゴリが混じる |
| レーダーを3グループの粒度で3枚、各5軸で出す | 上記により3グループが存在しない。軸はカテゴリの設問そのものなので、軸数を揃えるには設問を足し引きすることになり、表示の都合が設問構造を決める |
| 工程に「システム化方針の立案」を追加する | 何を作るかを決める行為であり、作ると決まったものを前提に始まる工程には属さない。ブロック3の業務理解と価値判断が持つ |
