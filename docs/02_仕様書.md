設計書 v1 と変更仕様 v1.1 を統合したものを土台とし、以後のレビューで確定した変更を直接この文書に反映する。この文書を唯一の正とする。

| 用語 | 意味 |

| 業務ジャンル | Webフロントエンド、ロボティクスなど、仕事の分野 |
| 工程 | 要件定義から運用保守まで、開発ライフサイクル上の位置 |
| スロット | 業務ジャンルの評価を4つに分けた切り口 |
| カテゴリ | 設問のまとまり |

| 隣接 | 守備範囲に接する未経験の領域 |
| 職種 | 分析結果に付くラベル。設問にはしない |

## 2. 目的と恩恵

### 2.1. 目的

自己評価を深めること。回答者が自分の現在地を言語化できる状態を目指す。
キャリアのイメージを明確にし、次に起こすべきアクションの明確化を行う。

### 2.2. 回答者が得る恩恵

回答者が記入後に得るものを4つに分ける。分析はこの4つを満たすために行う。

| ID | 恩恵 | 記入後に言えるようになること | 必要な情報 |
| --- | --- | --- | --- |
| B1 | 経験範囲を人に説明できる | 「Webバックエンドで要件定義から運用まで担当してきた」 | 経験した分野と工程、それぞれの深さ |
| B2 | 次に何を経験すれば範囲が広がるか分かる | 「基本設計はまだだが、隣なので手が届く」 | 今の位置に近い、未経験または浅い分野と工程 |
| B3 | 今の仕事の中で何を深めればいいか分かる | 「テストは担当しているが浅い」 | 経験済みで値が低い観点 |
| B4 | 分野が変わっても持っていけるものが分かる | 「デバッグ力は組込みに移っても使える」 | 分野に依存しない能力の値 |

B1が現在の範囲、B2が範囲の外側、B3が範囲の内側、B4が分野を横断するもの。排他かつ網羅とする。

### 2.3. 対象と範囲

| 項目 | 内容 |
| --- | --- |
| 対象者 | IT分野のエンジニア |
| 対象範囲 | IT分野のみ。MS / ME / EL / CH は対象外 |
| 使い方 | 本人の振り返りと、上長との面談の材料 |

### 2.4. 恩恵に含めないもの

他者との比較、総合評価、等級、職種の適合度％、順位。根拠は別資料「キャリアプランシート_エビデンス編」に記す。

### 2.5. 設計ルール

1. 同じまとまりの中の設問は同質であること
2. 汎用能力の観点に、分野名・製品名・分野固有の設計様式を書かないこと。技術名は書いてよい
3. 職種名を設問にしないこと
4. 同じ能力を2箇所で測らないこと。測る対象が違う重複は許容し、集約時に足し合わせない

## 3. 全体構造

### 3.1. 現在地の表し方

回答者の現在地は、業務ジャンルと工程の2つで表す。この組み合わせが守備範囲になる。
職種名は設問にせず、分析結果に付けるラベルとして扱う。

### 3.2. ブロック構成

設問を3つのブロックに分ける。分ける基準は、何を測るかである。

| ブロック | 測るもの | 回答対象 |
| --- | --- | --- |
| 基本情報 | なし（入力者の情報） | 全員 |
| 1. 業務ジャンル | どの分野で仕事をしてきたか。分野固有の技術 | 経験のあるジャンルのみ |
| 2. 工程能力 | ライフサイクルのどの局面を担当したか | 経験のある工程のみ |
| 3. 汎用能力 | ブロック1でもブロック2でも測れない力 | 全員 |

### 3.3. 回答方式

選択という操作を設けない。開いて答えれば選択したことになり、開かなければ未経験として扱う。

1. 自身が関与していないものはジャンル単位で折りたためるようにする。工程も同じ形にする
2. 全展開を初期値にしてもよい
3. 折りたたみ時も代表技術を表示する。ジャンル名だけでは自分が該当するか判断できない回答者がいるため
4. データ上は選択フラグを持たない。回答の有無が選択を兼ねる

### 3.4. アンカー

アンカーは2つ用意する。型はブロック単位で選ぶ。

| 値 | 習熟度型 | 関与型 |
| --- | --- | --- |
| 5 | 人に教えられる。より良いやり方を提案できる | 進め方や標準を定め、他者を導いた |
| 4 | 実務で必要に応じて、自分で行える | 主担当として、一人で完結させた |
| 3 | やればできるが、時間がかかる | 担当した |
| 2 | 知識はあるが、実務では行っていない | 補助・部分的に関わった |
| 1 | できない | 未経験 |

ブロックごとの対応は以下のとおり。

| ブロック | 型 |
| --- | --- |
| 1 業務ジャンル | 習熟度型 |
| 2 工程能力 | 関与型 |
| 3 汎用能力 | 習熟度型 |

ブロック1とブロック3は何ができるかを聞くので習熟度型を使う。ブロック2はどう担当したかを聞くので関与型を使う。
ブロック2に習熟度型を当てると、値2「知識はあるが、実務では行っていない」がその工程を担当していないことと同義になり、担当の有無が読めなくなる。

アンカーは表記統一のための道具ではなく、自己評価の精度を担保する仕組みである。
順位や比較を出さない設計では、判断の基準はアンカーしか存在しない。

ジャンル、工程、カテゴリ、観点のすべてに、表示名とは独立した固定IDを付与する。

### 4.3. ブロック2：工程能力

- 目的：ライフサイクル上のどこを担当し、理解しているかを把握する
- 経験のある工程のみ回答。アンカーは関与型
- 設問は仕事の単位で書く。職務経歴書に「〜を担当した」と書ける粒度とする
- 担当したかどうかを聞く。技術の中身はブロック3が持つ
- 工程には順序があるので、守備範囲マップの横軸になる

#### 4.3.1. 要件定義（4観点）

1. 顧客・利用者へのヒアリング
2. 現行業務・現行システムの分析
3. 要件の定義と要件定義書の作成
4. ステークホルダー間の合意形成

#### 4.3.2. 基本設計（4観点）

1. 基本的なシステムの構成設計（機能の組み合わせ）
2. 外部システムとの連携方式の設計
3. 非機能要件の実現方式の設計（性能・可用性・セキュリティ）
4. 基本設計書の作成と顧客への説明・承認取得

#### 4.3.3. 詳細設計（3観点）

1. 単一機能の内部仕様の作成
2. データ構造やアルゴリズム選定
3. 機能をまたぐ共通仕様の設計（ログ、機能間インタフェース）

#### 4.3.4. 実装（4観点）

1. 機能の実装（新規開発・既存改修）
2. 他者のコードのレビュー
3. 原因不明の不具合の切り分けと原因解析
4. 性能・リソースのチューニング

#### 4.3.5. テスト（4観点）

1. テスト計画の策定
2. テストケースの設計と実施
3. 非機能テスト（性能・負荷・セキュリティ）の実施
4. 受入テスト・ユーザーテストの支援

#### 4.3.6. 運用・保守（5観点）

1. 運用設計・監視設計
2. 日常運用・監視と障害対応
3. 問い合わせ・ユーザー対応
4. 変更管理・本番リリース作業
5. 改修要望の受付と対応方針の整理

### 4.4. ブロック3：汎用能力

- 目的：ブロック1でもブロック2でも測れない力を把握する
- 全員が回答。5カテゴリ・計19問。アンカーは習熟度型
- 設問は力の単位で書く。スキルシートに「〜ができる」と書ける粒度とする
- 設問に分野名・製品名・分野固有の設計様式を書かない。技術名は書いてよい
- 1設問には1つの能力だけを入れる。複数の能力を1問にまとめると、回答者が何をもって「できた」と言えるか判断できなくなる

カテゴリは階層を持たない。カテゴリごとの設問数は揃えない。

各設問に説明文を付ける。説明文は設問名の解釈が広がるのを防ぐために書き、設問名の言い換えは書かない。
文体は「〜できる」で揃える。アンカーが習熟度型であり、値の判定が「できるかどうか」であるため。
説明文の例示には分野を横断するものだけを使う。特定分野の攻撃名、製品名、設計様式名は書かない。

設問名は名詞句で短く書く。例示は設問名に括弧で添えず、説明文に書く。
同じカテゴリの設問は、対象物が互いに重ならない名前にする。名前が広いと、他の設問を含んでいるように読まれる。

カテゴリ内の設問は、日常業務で出会う頻度が高いものから並べる。難易度順とはしない。
難易度は観測できず、また番号の後ろほど上位という読みが、順位を出さないという設計と衝突するためである。

#### 4.4.1. 設計力（4問）

| # | 設問 | 説明 |
| --- | --- | --- |
| 1 | エラー・例外設計 | 異常をどこで検知し、どこで処理し、どこまで呼び出し元に伝えるかを決められる。処理を続けるか止めるか、何を記録するかの方針を立てられる |
| 2 | モジュール・依存関係の設計 | オブジェクト指向やデザインパターンなど確立された設計の型を踏まえて、機能をどの単位の部品に分け、部品どうしの依存をどう決めるかを判断できる。変更の影響が一箇所に収まる構造にできる |
| 3 | データ構造・アルゴリズムの選択 | 扱うデータの量と増え方に合わせて、保持の仕方と処理の手順を選べる。データが増えても破綻しない選択ができる |
| 4 | 性能・可用性の設計 | 求められる応答速度や停止許容時間から逆算して、全体の構成を決められる。負荷が集中する箇所や単一障害点を設計の段階で見つけられる |

#### 4.4.2. 実装力（5問）

| # | 設問 | 説明 |
| --- | --- | --- |
| 1 | 不具合・性能問題の原因特定 | 自分が書いていないコードを読んで処理の流れを追える。再現手順、ログ、計測結果から、動かない箇所や遅い箇所を絞り込める |
| 2 | リファクタリング | 動作を変えずにコードの構造を整理できる。どこから手を付けどこで止めるかを判断でき、壊していないことを確かめる手段を用意できる |
| 3 | セキュアな実装 | 外部から入る値を信用せずに検証し、権限の確認と秘密情報の扱いを実装できる。既知の攻撃手口を踏まえて書ける |
| 4 | メモリ・リソース管理 | 確保したメモリ、ファイル、接続などを使い終わった時点で確実に解放できる。リークや枯渇の原因を追える |
| 5 | 並行・非同期処理 | 複数の処理を同時に動かす実装ができる。競合、順序の入れ替わり、待ち合わせの不具合を避ける手当てができる |

#### 4.4.3. 技術判断と基盤構築（3問）

| # | 設問 | 説明 |
| --- | --- | --- |
| 1 | 技術選定と検証 | 未経験のものを含めて複数の技術を調べ、小さく試したうえで、何を得て何を失うかを整理して選べる。選んだ理由が後から追える形で残せる |
| 2 | リリース方式の設計 | 本番環境へどう出すかを決められる。停止時間、影響範囲、切り戻しの手順を織り込める |
| 3 | CI/CDの構築・運用 | ビルド、テスト、配置が自動で流れる仕組みを組める。失敗したときに原因が分かる形にできる |

## 5. 分析仕様

分析は 2.2 の恩恵 B1〜B4 を満たすために行う。出力と恩恵の対応は以下のとおり。

| 恩恵 | 主となる出力 | 補助の出力 |
| --- | --- | --- |
| B1 経験範囲を説明できる | 対応可能なポジション（5.5） | 守備範囲の職種（5.4）、守備範囲マップの塗り部分（5.2） |
| B2 次に広がる範囲が分かる | 関連職種（5.4） | 守備範囲マップの隣接部分（5.2） |
| B3 深めるべき点が分かる | 課題・改善内容（5.6） | — |
| B4 持っていけるものが分かる | 汎用能力の明細表（5.3） | — |

### 5.1. 値の扱い

未回答は未経験と同じ扱いとし、値1とする。別の状態は持たない。

| 値 | 扱い |
| --- | --- |
| 4〜5 | 守備範囲の職種および対応可能なポジションの根拠として使う |
| 2〜3 | 課題・改善内容として抽出する |
| 1 | 課題にしない。守備範囲に接していれば隣接および関連職種として表示する |

値1を課題にしない理由は、未経験を「できていないこと」として並べても打ち手にならないため。
未経験のうち手が届くものは、隣接および関連職種として別に表示する。手が届くかどうかはジャンルの関連表が定める。

### 5.2. 守備範囲マップ

B1（塗り部分）とB2（隣接部分）の補助の出力。

| 項目 | 内容 |
| --- | --- |
| 読み取るもの | どの分野のどの工程まで担当してきたか。次に伸ばしやすい領域はどこか |
| 元データ | 縦がブロック1、横がブロック2 |
| 形式 | 縦18行（未回答も含む全ジャンル、グループ順）× 横6列（工程） |

行と列の有効判定は以下のとおり。

| 対象 | 有効になる条件 |
| --- | --- |
| ジャンルの行 | S1〜S4の平均が2以上 |
| 工程の列 | その工程の観点の平均が2以上 |

工程はジャンルに依存しない回答者の属性なので、有効な工程は列全体に色が付く。ジャンルも同様に行全体に色が付く。

| セルの表示 | 条件 |
| --- | --- |
| 濃い塗り | 行と列がともに有効。守備範囲 |
| 薄い帯 | 行または列の一方のみ有効 |
| 破線 | 有効な行と隣接列、または隣接行と有効な列が交わる位置。隣接 |
| 無地 | 上記以外。範囲外 |

隣接の判定は以下のとおり。

1. 列の隣接は、有効な工程に隣り合う無効な工程
2. 行の隣接は、有効なジャンルとジャンルの関連表で結ばれた無効なジャンル

列は工程の順序を使い、行は関連表を使う。工程には順序があるので隣り合うことに意味があるが、ジャンルには順序がないため、表の並び順は判定に使わない。

塗りの濃さはジャンルの重み付け（S1〜S4の平均）を表す。
列ヘッダーの下に工程の重み付け、行ラベルの下にジャンルの重み付けをバーで表示する。

### 5.3. レーダーチャート

工程集約と業務ジャンル別はB1の内訳を示す。

| 枚数 | 内容 | 軸 |
| --- | --- | --- |
| 1 | 工程集約 | 6工程。値は各工程の観点の平均 |
| 回答数ぶん | 業務ジャンル別 | S1〜S4。全ジャンル共通軸なので比較できる |

工程別の観点値と、汎用能力の設問値は、レーダーではなく表で表示する。

### 5.4. 職種名

ジャンルに職種名のラベルを付ける。B1では自分が到達した分野の名前を、B2では次に手が届く分野の名前を示す。

| 項目 | 内容 |
| --- | --- |
| 読み取るもの | 自分の分野に付く職種名と、次に手が届く分野の職種名 |
| 元データ | ブロック1の各ジャンルの重み付けと、ジャンルの関連表 |
| 出力内容 | 職種名と、その根拠を箇条書き |
| 出さないもの | 順位、適合度％ |
| 表示件数の上限 | なし |
| 表示順 | ジャンル定義順。値による並べ替えは行わない |

2つに分けて出力する。職種名はジャンルと職種の対応表から引く。

| 出力 | 恩恵 | 対象になるジャンル |
| --- | --- | --- |
| 守備範囲の職種 | B1 | 重み付けが3.5以上 |
| 関連職種 | B2 | 守備範囲の職種のジャンルと関連表で結ばれており、自身の重み付けが3.5未満 |

重み付けはS1〜S4の平均であり、全スロットが3以下では3.0を超えない。判定値3.5は、値4以上のスロットを最低1つ持つジャンルだけを守備範囲の職種の対象にする。5.1の値の扱いと対応する。

根拠の箇条書きは以下を挙げる。

1. 守備範囲の職種は、そのジャンルの重み付け
2. 関連職種は、結ばれている相手のジャンル名と、関連表が記す関連の根拠

同じグループに属することは関連職種の根拠にしない。グループは表の見出しであり、ジャンルどうしの近さを表さないため。

工程から算出する役割は対応可能なポジションが扱う。本節はジャンルから算出する分野の名前だけを扱う。

### 5.5. 対応可能なポジション

B1の主となる出力。工程の重み付けをもとに、いま担える役割の範囲を示す。

| 項目 | 内容 |
| --- | --- |
| 読み取るもの | 自分の役割がどこまで広がっているか |
| 元データ | ブロック2の各工程の重み付けと、一部の汎用能力カテゴリ |
| 出力内容 | ポジション名と、その根拠となった工程・カテゴリを箇条書き |
| 出さないもの | 順位、適合度％ |

ポジションは性質の異なる2種類に分ける。

| 種別 | 定義 |
| --- | --- |
| 単一的ポジション | 工程1つ、または隣接する複数工程に、独立して到達していることを示す基礎ポジション |
| 上位職 | 対応する単一的ポジションの条件を包含し、そこに汎用能力カテゴリの条件を上乗せして初めて成立する応用ポジション |

ポジション名と2種類への分類は確定する（REQ-212）。

| 種別 | ポジション |
| --- | --- |
| 単一的ポジション | システムエンジニア、プログラマー、テスター・QA、運用担当 |
| 上位職 | システムコンサルタント、アーキテクト、テックリード、プロジェクトリーダー、プロジェクトマネージャー、プロダクトマネージャー |

上位職は、土台にする単一的ポジションの条件を満たしたうえで、汎用能力側の条件を上乗せして成立する。
土台の条件は上位職側に書き直さない。上位職の条件が土台の条件を含むため。

判定条件は未定。工程・汎用能力の具体的な数値と、各上位職がどの単一的ポジションを土台にするかの
割り当ての両方が確定していない。候補となる設計は REQ-239 にある。

数値は動かした出力を見て調整することが前提であり、調整前の数値は本書に置かない。

2. レーダーチャート（工程集約1枚、ジャンル別）
3. 職種名（守備範囲の職種、関連職種）
4. 対応可能なポジション
5. 課題・改善内容
6. 明細表（工程別の観点値、汎用能力のカテゴリ別の設問値）

強みは別枠で表示しない。職種名と対応可能なポジションの根拠として現れる。
