## 1. この資料について

キャリアプランシートの設問、分析、データ、画面の仕様を定める。
設計書 v1 と変更仕様 v1.1 を統合したものを土台とし、以後のレビューで確定した変更を直接この文書に反映する。この文書を唯一の正とする。

prototype（動作サンプル、prototype/sample_v1.html）はv1のまま凍結し、本書の版番号とは連動させない。v1.1からの変更点は要求仕様書（01_要求仕様書.md）を参照。

| 章 | 内容 |

| 2 | 目的と恩恵、範囲 |

| 4 | 設問仕様 |
| 5 | 分析仕様 |

用語は以下の意味で使う。

| 用語 | 意味 |
| --- | --- |
| 業務ジャンル | Webフロントエンド、ロボティクスなど、仕事の分野 |
| 工程 | 要件定義から運用保守まで、開発ライフサイクル上の位置 |
| スロット | 業務ジャンルの評価を4つに分けた切り口 |

| 隣接 | 守備範囲に接する未経験の領域 |
| 職種 | 分析結果に付くラベル。設問にはしない |

## 2. 目的と恩恵

### 2.1. 目的

自己評価を深めること。回答者が自分の現在地を言語化できる状態を目指す。
キャリアのイメージを明確にし、次に起こすべきアクションの明確化を行う。

### 2.2. 回答者が得る恩恵

回答者が記入後に得るものを4つに分ける。分析はこの4つを満たすために行う。

| ID | 恩恵 | 記入後に言えるようになること | 必要な情報 |
| --- | --- | --- | --- |
| B1 | 経験範囲を人に説明できる | 「Webバックエンドで要件定義から運用まで担当してきた」 | 経験した分野と工程、それぞれの深さ |
| B2 | 次に何を経験すれば範囲が広がるか分かる | 「基本設計はまだだが、隣なので手が届く」 | 今の位置に近い、未経験または浅い分野と工程 |
| B3 | 今の仕事の中で何を深めればいいか分かる | 「テストは担当しているが浅い」 | 経験済みで値が低い観点 |
| B4 | 分野が変わっても持っていけるものが分かる | 「デバッグ力は組込みに移っても使える」 | 分野に依存しない能力の値 |

B1が現在の範囲、B2が範囲の外側、B3が範囲の内側、B4が分野を横断するもの。排他かつ網羅とする。

### 2.3. 対象と範囲

| 項目 | 内容 |
| --- | --- |
| 対象者 | IT分野のエンジニア |
| 対象範囲 | IT分野のみ。MS / ME / EL / CH は対象外 |
| 使い方 | 本人の振り返りと、上長との面談の材料 |

### 2.4. 恩恵に含めないもの

他者との比較、総合評価、等級、職種の適合度％、順位。根拠は別資料「キャリアプランシート_エビデンス編」に記す。

### 2.5. 設計ルール

1. 1カテゴリ内の観点は同質であること
2. 汎用能力の観点はジャンル中立に書くこと
3. 職種名を設問にしないこと
4. 同じ能力を2箇所で測らないこと。測る対象が違う重複は許容し、集約時に足し合わせない

## 3. 全体構造

### 3.1. 現在地の表し方

回答者の現在地は、業務ジャンルと工程の2つで表す。この組み合わせが守備範囲になる。
職種名は設問にせず、分析結果に付けるラベルとして扱う。

### 3.2. ブロック構成

設問を3つのブロックに分ける。分ける基準は、その能力がジャンルを移っても使えるかどうか。

| ブロック | 評価するもの | 能力の影響度 | 回答対象 |
| --- | --- | --- | --- |
| 基本情報 | なし（入力者の情報） | — | 全員 |
| 1. 業務ジャンル | そのジャンルでしか使えない技術 | 独立 | 経験のあるジャンルのみ |
| 2. 工程能力 | どの工程を担当し、理解しているか | 部分的に共通 | 経験のある工程のみ |
| 3. 汎用能力 | ジャンル・工程を横断する力 | 共通 | 全員 |

### 3.3. 回答方式

選択という操作を設けない。開いて答えれば選択したことになり、開かなければ未経験として扱う。

1. 自身が関与していないものはジャンル単位で折りたためるようにする。工程も同じ形にする
2. 全展開を初期値にしてもよい
3. 折りたたみ時も代表技術を表示する。ジャンル名だけでは自分が該当するか判断できない回答者がいるため
4. データ上は選択フラグを持たない。回答の有無が選択を兼ねる

### 3.4. アンカー

アンカーは3つ用意する。型はカテゴリ単位で選ぶ。同一カテゴリ内で揃っていればよい。

| 値 | A 自立度型 | B 関与深度型 | C 実践頻度型 |
| --- | --- | --- | --- |
| 5 | 標準を定め、他者を指導できる | 組織に展開した | 定着させ、他者にも広めた |
| 4 | 一人で完結でき、判断もできる | 主担当として責任を持った | 常時実践している |
| 3 | 指示があれば一人でできる | 担当した | 複数回 |
| 2 | 補助・部分的に関わった | 補助として関わった | 一度だけ |
| 1 | 未経験 | 未経験 | 未経験 |

カテゴリごとの対応は以下のとおり。

| カテゴリ | 型 |
| --- | --- |
| ブロック1 業務ジャンル（S1〜S4） | A |
| ブロック2 工程能力（全6） | A |
| G1 開発・実装（全4） | A |
| G2-1 開発基盤・自動化 | A |
| G2-2 開発プロセス・手法 | C |
| G2-3 技術選定・判断 | A |
| G2-4 学習・技術調査 | C |
| G3-1 技術コミュニケーション | A |
| G3-2 チーム運営・リーダーシップ | A |
| G3-3 顧客・ステークホルダー対応 | B |
| G3-4 セルフマネジメント | A |

アンカーは表記統一のための道具ではなく、自己評価の精度を担保する仕組みである。
順位や比較を出さない設計では、判断の基準はアンカーしか存在しない。

観点ごとの文言は作らない。共通アンカーで運用し、実際に迷いが出た観点にだけ後から足す。

### 4.3. ブロック2：工程能力

- 目的：ライフサイクル上のどこを担当し、理解しているかを把握する
- 経験のある工程のみ回答。6工程・計38観点（最大38問）。アンカーA
- 設問文は行為で書く。能力の表現はブロック3が持つ
- 工程には順序があるので、守備範囲マップの横軸になる

工程ごとに観点数が異なってよい。工程のレーダーは6工程を軸にした集約1枚であり、観点数の差は影響しない。

### 4.4. ブロック3：汎用能力

- 目的：ジャンルにも工程にも紐づかない力を把握する。別のジャンルへ移れるかはこのブロックの厚みで読む
- 全員が回答。3グループ × 4カテゴリ × 4観点（48問）
- カテゴリは「何に作用する力か」で分ける
- 観点はジャンル中立に書く

グループ内のカテゴリ数は揃える必要がない。レーダーの軸は4から6の範囲であれば読める。
カテゴリのドリルダウンはレーダーではなく表で表示する。

## 5. 分析仕様

分析は 2.2 の恩恵 B1〜B4 を満たすために行う。出力と恩恵の対応は以下のとおり。

| 恩恵 | 主となる出力 | 補助の出力 |
| --- | --- | --- |
| B1 経験範囲を説明できる | 対応可能なポジション（5.5） | 守備範囲マップの塗り部分（5.2） |
| B2 次に広がる範囲が分かる | 関連職種（5.4） | 守備範囲マップの隣接部分（5.2） |
| B3 深めるべき点が分かる | 課題・改善内容（5.6） | — |
| B4 持っていけるものが分かる | 汎用能力のレーダー（5.3） | — |

### 5.1. 値の扱い

未回答は未経験と同じ扱いとし、値1とする。別の状態は持たない。

| 値 | 扱い |
| --- | --- |
| 4〜5 | 関連職種および対応可能なポジションの根拠として使う |
| 2〜3 | 課題・改善内容として抽出する |
| 1 | 課題にしない。守備範囲に接していれば隣接として表示する |

値1を課題にしない理由は、未経験を「できていないこと」として並べても打ち手にならないため。
未経験のうち手が届くものは、隣接として別に表示する。

### 5.2. 守備範囲マップ

B1（塗り部分）とB2（隣接部分）の補助の出力。

| 項目 | 内容 |
| --- | --- |
| 読み取るもの | どの分野のどの工程まで担当してきたか。次に伸ばしやすい領域はどこか |
| 元データ | 縦がブロック1、横がブロック2 |
| 形式 | 縦18行（未回答も含む全ジャンル、グループ順）× 横6列（工程） |

行と列の有効判定は以下のとおり。

| 対象 | 有効になる条件 |
| --- | --- |
| ジャンルの行 | S1〜S4の平均が2以上 |
| 工程の列 | その工程の観点の平均が2以上 |

工程はジャンルに依存しない回答者の属性なので、有効な工程は列全体に色が付く。ジャンルも同様に行全体に色が付く。

| セルの表示 | 条件 |
| --- | --- |
| 濃い塗り | 行と列がともに有効。守備範囲 |
| 薄い帯 | 行または列の一方のみ有効 |
| 破線 | 有効な行と隣接列、または隣接行と有効な列が交わる位置。隣接 |
| 無地 | 上記以外。範囲外 |

隣接の判定は以下のとおり。

1. 列の隣接は、有効な工程に隣り合う無効な工程
2. 行の隣接は、同じグループ内で有効なジャンルに隣り合う無効なジャンル

塗りの濃さはジャンルの重み付け（S1〜S4の平均）を表す。
列ヘッダーの下に工程の重み付け、行ラベルの下にジャンルの重み付けをバーで表示する。

### 5.3. レーダーチャート

汎用能力の3枚がB4の主となる出力。工程集約と業務ジャンル別はB1の内訳を示す。

| 枚数 | 内容 | 軸 |
| --- | --- | --- |
| 3 | 汎用能力（G1、G2、G3） | 各グループの4カテゴリ。値はカテゴリ内4観点の平均 |
| 1 | 工程集約 | 6工程。値は各工程の観点の平均 |
| 回答数ぶん | 業務ジャンル別 | S1〜S4。全ジャンル共通軸なので比較できる |

工程別の観点値と、汎用能力のカテゴリ別観点値は、レーダーではなく表で表示する。

### 5.4. 関連職種

B2の主となる出力。まだ届いていないが近い職種名を出す。すでに該当している職種は5.5で扱う。

| 項目 | 内容 |
| --- | --- |
| 読み取るもの | 次に手が届く分野の職種名 |
| 元データ | ブロック1の各ジャンルの重み付けと、ジャンルのグループ定義 |
| 出力内容 | 職種名と、その根拠を箇条書き |
| 出さないもの | 順位、適合度％ |
| 表示件数の上限 | なし |
| 表示順 | ジャンル定義順。値による並べ替えは行わない |

出力条件は以下の両方を満たすジャンル。判定値は暫定であり、要求仕様書REQ-222で扱う。

1. 同じグループ内に、重み付けが3.5以上のジャンルが1つ以上ある
2. そのジャンル自身の重み付けが3.5未満

根拠の箇条書きには、条件1に該当した同グループのジャンル名を挙げる。

### 5.5. 対応可能なポジション

B1の主となる出力。工程の重み付けをもとに、いま担える役割の範囲を示す。

| 項目 | 内容 |
| --- | --- |
| 読み取るもの | 自分の役割がどこまで広がっているか |
| 元データ | ブロック2の各工程の重み付けと、一部の汎用能力カテゴリ |
| 出力内容 | ポジション名と、その根拠となった工程・カテゴリを箇条書き |
| 出さないもの | 順位、適合度％ |

ポジションは性質の異なる2種類に分ける。

| 種別 | 定義 |
| --- | --- |
| 単一的ポジション | 工程1つ、または隣接する複数工程に、独立して到達していることを示す基礎ポジション |
| 上位職 | 対応する単一的ポジションの条件を包含し、そこに汎用能力カテゴリの条件を上乗せして初めて成立する応用ポジション |

ポジション名と2種類への分類は確定する（REQ-212）。

| 種別 | ポジション |
| --- | --- |
| 単一的ポジション | システムエンジニア、プログラマー、テスター・QA、運用担当 |
| 上位職 | システムコンサルタント、アーキテクト、テックリード、プロジェクトリーダー、プロジェクトマネージャー |

判定条件は未定。工程・汎用能力の具体的な数値、および各上位職がどの単一的ポジションを土台にするかのどちらも依頼者と合意していない。REQ-216で検討する。

プロダクトマネージャーは候補としたが、判定の根拠となる観点が現行の設問セットにないため、v1.3には含めない。REQ-214・REQ-215として別管理する（要求仕様書6章）。
