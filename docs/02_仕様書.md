# エンジニア キャリアプランシート 仕様書 v2.2（IT分野）

## 1. この資料について

キャリアプランシートの目的、設問、分析結果、データ、画面の仕様を定める。
この資料では、回答者が自分の経験範囲と次に伸ばす領域を把握できるようにするため、入力項目、計算ルール、結果表示、保存形式を定義する。

| 章 | 内容 |
| --- | --- |
| 2 | 目的、回答者が得る恩恵、対象範囲、設計ルール |
| 3 | 入力と分析に共通する構造、アンカー、識別子、平均値 |
| 4 | 回答者に提示する設問と入力項目 |
| 5 | 入力値から作る分析結果と、結果に出す内容 |
| 6 | JSON保存、JSON読み込み、互換性 |
| 7 | 入力画面と結果画面の表示・操作 |

用語は以下の意味で使う。

| 用語 | 意味 |
| --- | --- |
| 業務ジャンル | Webフロントエンド、ロボティクスなど、仕事の分野 |
| 工程 | 要件定義から運用保守まで、開発ライフサイクル上の位置 |
| スロット | 業務ジャンルの評価を4つに分けた切り口 |
| カテゴリ | 汎用能力設問のまとまり |
| 観点 | 工程能力の中の設問1つ |
| 設問 | 回答者が5段階で回答する最小単位 |
| アンカー | 5段階の各段が何を意味するかの定義 |
| 平均評価値 | ジャンル、工程、汎用能力カテゴリに属する評価値の平均 |
| 守備範囲 | 経験のあるジャンルと経験のある工程が重なる領域 |
| 関連 | ジャンルどうしの近さ。ジャンルの関連表が定める |
| 隣接 | 守備範囲に接する未経験の領域 |
| 職種 | 分析結果に付くラベル。設問にはしない |
| ポジション | 工程能力と汎用能力から判定する役割ラベル |
| 結果カード | 結果画面に表示する出力のまとまり |

## 2. 目的と恩恵

### 2.1. 目的

自己評価を深めること。回答者が自分の現在地を言語化できる状態を目指す。
キャリアのイメージを明確にし、次に起こすべきアクションを具体化する。

### 2.2. 回答者が得る恩恵

回答者が記入後に得るものを4つに分ける。分析はこの4つを満たすために行う。

| ID | 恩恵 | 記入後に言えるようになること | 必要な情報 | 主な結果出力 |
| --- | --- | --- | --- | --- |
| B1 | 経験範囲を人に説明できる | 「Webバックエンドで要件定義から運用まで担当してきた」 | 経験した分野と工程、それぞれの深さ | 守備範囲マップ、守備範囲の職種、対応可能なポジション |
| B2 | 次に何を経験すれば範囲が広がるか分かる | 「基本設計はまだだが、隣なので手が届く」 | 今の位置に近い、未経験または浅い分野と工程 | 守備範囲マップの隣接、関連職種 |
| B3 | 今の仕事の中で何を深めればいいか分かる | 「テストは担当しているが浅い」 | 経験済みで値が低い観点 | 課題・改善内容 |
| B4 | 分野が変わっても持っていけるものが分かる | 「デバッグ力は組込みに移っても使える」 | 分野に依存しない能力の値 | 汎用能力のレーダーチャート、明細表 |

B1が現在の範囲、B2が範囲の外側、B3が範囲の内側、B4が分野を横断するもの。排他かつ網羅とする。

### 2.3. 対象と範囲

| 項目 | 内容 |
| --- | --- |
| 対象者 | IT分野のエンジニア |
| 対象範囲 | IT分野のみ。MS / ME / EL / CH は対象外 |
| 使い方 | 本人の振り返りと、上長との面談の材料 |

### 2.4. 恩恵に含めないもの

他者との比較、総合評価、等級、職種の適合度％、順位は出さない。
根拠は別資料「キャリアプランシート_エビデンス編」に記す。

### 2.5. 設計ルール

1. 同じまとまりの中の設問は同質であること
2. 汎用能力の観点に、分野名・製品名・分野固有の設計様式を書かないこと。技術名は書いてよい
3. 職種名を設問にしないこと
4. 同じ能力を2箇所で測らないこと。測る対象が違う重複は許容し、集約時に足し合わせない
5. 固定IDは表示名とは独立させること。表示名の変更で過去データが読めなくならないようにする
6. 設問一覧を表にする場合は、1行に1設問を書くこと。複数の設問を1つのセルに詰め込まない

## 3. 全体構造

### 3.1. 現在地の表し方

回答者の現在地は、業務ジャンルと工程の2つで表す。この組み合わせが守備範囲になる。
職種名は設問にせず、分析結果に付けるラベルとして扱う。

### 3.2. ブロック構成

設問を3つのブロックに分ける。分ける基準は、何を測るかである。

| ブロック | 測るもの | 回答対象 |
| --- | --- | --- |
| 基本情報 | なし（入力者の情報） | 全員 |
| 1. 業務ジャンル | どの分野で仕事をしてきたか。分野固有の技術 | 経験のあるジャンルのみ |
| 2. 工程能力 | ライフサイクルのどの局面を担当したか | 全員 |
| 3. 汎用能力 | ブロック1でもブロック2でも測れない力 | 全員 |

### 3.3. 回答方式

選択という操作を設けない。開いて答えれば選択したことになり、開かなければ未経験として扱う。

1. 自身が関与していないものはジャンル単位で折りたためるようにする。工程も同じ形にする
2. 初期状態は折りたたみとする。ただし、全員が回答する必須のまとまりは初期状態で開いて表示する
3. 折りたたみ時も代表技術を表示する。ジャンル名だけでは自分が該当するか判断できない回答者がいるため
4. データ上は選択フラグを持たない。回答の有無が選択を兼ねる

### 3.4. アンカー

アンカーは2つ用意する。型はブロック単位で選ぶ。
画面上のラジオボタンには短い表示ラベルを使い、判断基準は凡例、補足、ツールチップなどで確認できるようにする。
ボタン内に長い文章を入れると、選択肢の幅が不揃いになり、回答者が値ではなく文章量に引っ張られるためである。

| 値 | 習熟度型の表示ラベル | 習熟度型の判断基準 | 関与型の表示ラベル | 関与型の判断基準 |
| --- | --- | --- | --- | --- |
| 5 | 指導・改善提案 | 人に教えられる。より良いやり方を提案できる | 標準化・主導 | 進め方や標準を定め、他者を導いた |
| 4 | 自力で実務対応 | 実務で必要に応じて、自分で行える | 主担当で完結 | 主担当として、一人で完結させた |
| 3 | 時間をかければ可能 | やればできるが、時間がかかる | 担当 | 担当した |
| 2 | 知識のみ | 知識はあるが、実務では行っていない | 補助・部分担当 | 補助・部分的に関わった |
| 1 | できない | できない | 未経験 | 未経験 |

ブロックごとの対応は以下のとおり。

| ブロック | 型 |
| --- | --- |
| 1 業務ジャンル | 習熟度型 |
| 2 工程能力 | 関与型 |
| 3 汎用能力 | 習熟度型 |

ブロック1とブロック3は何ができるかを聞くので習熟度型を使う。ブロック2はどう担当したかを聞くので関与型を使う。
ブロック2に習熟度型を当てると、値2「知識はあるが、実務では行っていない」がその工程を担当していないことと同義になり、担当の有無が読めなくなる。

アンカーは表記統一のための道具ではなく、自己評価の精度を担保する仕組みである。
順位や比較を出さない設計では、判断の基準はアンカーしか存在しない。

### 3.5. 識別子

### 3.6. 平均評価値と有効判定

分析に使う平均評価値は、対象に属する回答値の単純平均とする。表示時は小数第2位まで表示する。

| 対象 | 算出方法 | 有効になる条件 | 主な利用先 |
| --- | --- | --- | --- |
| 業務ジャンル | S1〜S4の平均 | 平均評価値が2以上 | 守備範囲マップの行 |
| 工程 | その工程の観点値の平均 | 平均評価値が2以上 | 守備範囲マップの列 |
| 汎用能力カテゴリ | そのカテゴリの設問値の平均 | 有効判定は行わない | 対応可能なポジションの判定材料、明細表 |

職種名は、業務ジャンルの平均評価値が2.75以上3.5未満であれば見習い職種、3.5以上であれば守備範囲の職種として扱う。課題・改善内容は、平均ではなく個別値が2または3の項目を対象とする。

## 4. 設問仕様

### 4.1. 基本情報

| ID | 項目 | 入力形式 |
| --- | --- | --- |
| `name` | 氏名 | テキスト |
| `employeeNo` | 社員番号 | テキスト |
| `department` | 所属 | テキスト |
| `specialty` | 専門分野 | テキスト |
| `experienceYears` | エンジニア経験年数 | 選択 |

エンジニア経験年数の選択肢は、`1-3`、`4-9`、`10-19`、`20以上` とする。

### 4.3. ブロック2：工程能力

- 目的：ライフサイクル上のどこを担当し、理解しているかを把握する
- 全員が回答。未経験の工程は値1「未経験」として回答する。アンカーは関与型
- 設問は仕事の単位で書く。職務経歴書に「〜を担当した」と書ける粒度とする
- 担当したかどうかを聞く。技術の中身はブロック3が持つ
- 工程には順序があるので、守備範囲マップの横軸になる

JSONでは、工程IDの配下に本節の記載順で1から始まる観点キーを持つ。

#### 4.3.1. 要件定義（`requirements`、4観点）

1. 顧客・利用者へのヒアリング
2. 現行業務・現行システムの分析
3. 要件の定義と要件定義書の作成
4. ステークホルダー間の合意形成

#### 4.3.2. 基本設計（`basic-design`、4観点）

1. 基本的なシステムの構成設計（機能の組み合わせ）
2. 外部システムとの連携方式の設計
3. 非機能要件の実現方式の設計（性能・可用性・セキュリティ）
4. 基本設計書の作成と顧客への説明・承認取得

#### 4.3.3. 詳細設計（`detail-design`、3観点）

1. 単一機能の内部仕様の作成
2. データ構造やアルゴリズム選定
3. 機能をまたぐ共通仕様の設計（ログ、機能間インタフェース）

#### 4.3.4. 実装（`implementation`、4観点）

1. 機能の実装（新規開発・既存改修）
2. 他者のコードのレビュー
3. 原因不明の不具合の切り分けと原因解析
4. 性能・リソースのチューニング

#### 4.3.5. テスト（`test`、4観点）

1. テスト計画の策定
2. テストケースの設計と実施
3. 非機能テスト（性能・負荷・セキュリティ）の実施
4. 受入テスト・ユーザーテストの支援

#### 4.3.6. 運用・保守（`operation`、5観点）

1. 運用設計・監視設計
2. 日常運用・監視と障害対応
3. 問い合わせ・ユーザー対応
4. 変更管理・本番リリース作業
5. 改修要望の受付と対応方針の整理

### 4.4. ブロック3：汎用能力

- 目的：ブロック1でもブロック2でも測れない力を把握する
- 全員が回答。5カテゴリ・計19問。アンカーは習熟度型
- 設問は力の単位で書く。スキルシートに「〜ができる」と書ける粒度とする
- 設問に分野名・製品名・分野固有の設計様式を書かない。技術名は書いてよい
- 1設問には1つの能力だけを入れる。複数の能力を1問にまとめると、回答者が何をもって「できた」と言えるか判断できなくなる

カテゴリは階層を持たない。カテゴリごとの設問数は揃えない。

各設問に説明文を付ける。説明文は設問名の解釈が広がるのを防ぐために書き、設問名の言い換えは書かない。
文体は「〜できる」で揃える。アンカーが習熟度型であり、値の判定が「できるかどうか」であるため。
説明文の例示には分野を横断するものだけを使う。特定分野の攻撃名、製品名、設計様式名は書かない。

設問名は名詞句で短く書く。例示は設問名に括弧で添えず、説明文に書く。
同じカテゴリの設問は、対象物が互いに重ならない名前にする。名前が広いと、他の設問を含んでいるように読まれる。

カテゴリ内の設問は、日常業務で出会う頻度が高いものから並べる。難易度順とはしない。
難易度は観測できず、また番号の後ろほど上位という読みが、順位を出さないという設計と衝突するためである。

JSONでは、カテゴリIDの配下に本節の記載順で1から始まる設問キーを持つ。

## 5. 分析結果仕様

分析結果は 2.2 の恩恵 B1〜B4 を満たすために出力する。
本章では、入力値から分析用データを作り、判定条件を適用し、結果カードに表示するまでの仕様を定める。
JSONの保存形式は6章、画面上の表示順や操作は7章に記す。

### 5.1. 分析の流れ

分析は以下の順で行う。

| 順序 | 処理 | 内容 | 主な出力 |
| --- | --- | --- | --- |
| 1 | 入力値の正規化 | 未回答を値1として扱い、ブロックごとの回答値をそろえる | `genres`、`procs`、`gens` |
| 2 | 平均評価値の算出 | 業務ジャンル、工程、汎用能力カテゴリごとに平均評価値を作る | `genreAvg`、`procAvg`、`categoryAvg` |
| 3 | 判定 | 守備範囲、隣接、職種名、対応可能なポジション、課題・改善内容を判定する | 各結果カードの表示対象 |
| 4 | 結果カード出力 | 判定結果と根拠を、結果カードごとに表示する | 守備範囲マップ、汎用能力、職種名、対応可能なポジション、課題・改善内容、明細表 |

5.2と5.3では、カード間で共通して使うデータと値の扱いを定義する。
5.4では結果カードに共通する出力ルールを定義する。
5.5以降では、結果カードごとに「何を入力にし、どう判定し、何を表示するか」を定義する。

### 5.2. 分析用データ

入力値から以下の分析用データを作る。
分析用データは画面表示のために内部で作る値であり、JSONには保存しない。

| データ | 内容 | 算出方法 |
| --- | --- | --- |
| `genres` | 18ジャンルそれぞれのS1〜S4の値 | ブロック1の回答値。未回答は1 |
| `procs` | 6工程それぞれの観点値 | ブロック2の回答値。未回答は1 |
| `gens` | 5カテゴリそれぞれの設問値 | ブロック3の回答値。未回答は1 |
| `genreAvg` | ジャンルごとの平均評価値 | S1〜S4の平均 |
| `procAvg` | 工程ごとの平均評価値 | その工程の観点値の平均 |
| `categoryAvg` | 汎用能力カテゴリごとの平均評価値 | そのカテゴリの設問値の平均 |

### 5.3. 共通の値の扱い

未回答は未経験と同じ扱いとし、値1とする。別の状態は持たない。

| 値 | 扱い |
| --- | --- |
| 4〜5 | 守備範囲の職種および対応可能なポジションの根拠として使う |
| 2〜3 | 課題・改善内容として抽出する |
| 1 | 課題にしない。守備範囲に接していれば隣接および関連職種として表示する |

値1を課題にしない理由は、未経験を「できていないこと」として並べても打ち手にならないため。
未経験のうち手が届くものは、隣接および関連職種として別に表示する。手が届くかどうかはジャンルの関連表が定める。

### 5.4. 結果カード共通

結果カードは、回答者が得る恩恵B1〜B4を満たすために出力する。
各カードは、判定結果だけでなく、回答者が結果を確認できる根拠を合わせて表示する。

| 項目 | 内容 |
| --- | --- |
| 共通の表示方針 | 判定結果と、その根拠になる評価値または関連理由を表示する |
| 共通の表示順 | 7.3の結果画面の表示順に従う |
| 共通の空状態 | 該当する結果がない場合もカード自体は表示し、空欄または該当なしとして扱う |
| 共通して表示しない内容 | 順位、適合度％、おすすめ順、他者比較 |

### 5.5. 守備範囲マップ

どの業務ジャンルのどの工程まで担当してきたかと、次に伸ばしやすい領域を示す。

| 項目 | 内容 |
| --- | --- |
| 目的 | B1、B2を満たす |
| 入力 | `genreAvg`、`procAvg`、ジャンルの関連表 |
| 算出条件 | ジャンルの行はS1〜S4の平均が2以上、工程の列はその工程の観点値の平均が2以上で有効とする |
| 表示内容 | 縦18行（未回答を含む全ジャンル、グループ順）×横6列（工程）の表。列見出しに工程名と工程平均評価値、行見出しにジャンル名とジャンル平均評価値を表示する |
| 表示順 | 行はブロック1のジャンル定義順、列はブロック2の工程定義順 |
| 空状態 | 未回答でも全ジャンル・全工程を表示する |
| 根拠表示 | 行ラベルにジャンル平均評価値、列ヘッダーに工程平均評価値を表示する |
| 表示しない内容 | セル単位の点数 |

行と列の有効判定は以下のとおり。

| 対象 | 有効になる条件 |
| --- | --- |
| ジャンルの行 | S1〜S4の平均が2以上 |
| 工程の列 | その工程の観点の平均が2以上 |

工程はジャンルに依存しない回答者の属性なので、有効な工程は列全体に色が付く。ジャンルも同様に行全体に色が付く。

| セルの表示 | 条件 |
| --- | --- |
| 濃い塗り | 行と列がともに有効。守備範囲 |
| 薄い帯 | 行または列の一方のみ有効 |
| 破線 | 有効な行と隣接列、または隣接行と有効な列が交わる位置。隣接 |
| 無地 | 上記以外。範囲外 |

隣接の判定は以下のとおり。

1. 列の隣接は、有効な工程に隣り合う無効な工程
2. 行の隣接は、有効なジャンルとジャンルの関連表で結ばれた無効なジャンル

列は工程の順序を使い、行は関連表を使う。工程には順序があるので隣り合うことに意味があるが、ジャンルには順序がないため、表の並び順は判定に使わない。

塗りの濃さはジャンルの平均評価値（S1〜S4の平均）を表す。
列ヘッダーの下に工程の平均評価値、行ラベルの下にジャンルの平均評価値をバーで表示する。

### 5.6. 汎用能力のレーダーチャート

分野や工程が変わっても持っていける能力を、ブロック3のカテゴリごとに表示する。

| 項目 | 内容 |
| --- | --- |
| 目的 | B4を満たす |
| 入力 | `gens`、汎用能力のカテゴリ定義 |
| 算出条件 | カテゴリごとに、そのカテゴリに属する各設問の回答値をレーダーの軸にする。カテゴリ平均評価値は描画値に使わない |
| 表示内容 | カテゴリ数ぶんのレーダーチャート。各軸はそのカテゴリの設問名とし、値の範囲は1〜5とする |
| 表示順 | ブロック3の汎用能力カテゴリ定義順 |
| 空状態 | 全員が回答対象のため、常に表示する |
| 根拠表示 | 各軸に設問名と評価値を表示する |
| 表示しない内容 | 工程集約レーダー、業務ジャンル別レーダー、カテゴリをまたぐ重ね描き |

軸の数はカテゴリの設問数と一致する。カテゴリごとに設問数が違うため、軸の数も揃わない。
カテゴリをまたいだ形の比較は行わない。軸が別の設問であり、重ねて読む意味がないため。

業務ジャンルのスロット値と、工程別の観点値は、レーダーではなく表で表示する。

### 5.7. 職種名

ジャンルに職種名のラベルを付ける。B1では自分が到達した分野の名前を、B2では次に手が届く分野の名前を示す。

| 項目 | 内容 |
| --- | --- |
| 目的 | B1、B2を満たす |
| 入力 | `genreAvg`、ブロック1のジャンル定義表の職種名、ジャンルの関連表 |
| 算出条件 | 守備範囲の職種は平均評価値3.5以上、見習い職種は平均評価値2.75以上3.5未満、関連職種は守備範囲の職種のジャンルと関連表で結ばれ、自身の平均評価値が2.75未満のジャンルとする |
| 表示内容 | 守備範囲の職種、見習い職種、関連職種、根拠の箇条書き |
| 表示順 | ブロック1のジャンル定義順。表示件数の上限は設けない |
| 空状態 | 該当職種がない区分は空欄または該当なしとして表示する |
| 根拠表示 | 守備範囲の職種と見習い職種は平均評価値、関連職種は接続元ジャンル名と関連の根拠を表示する |
| 表示しない内容 | 共通ルール以外になし |

3つに分けて出力する。職種名はブロック1のジャンル定義表から引く。

| 出力 | 恩恵 | 対象になるジャンル |
| --- | --- | --- |
| 守備範囲の職種 | B1 | 平均評価値が3.5以上 |
| 見習い職種 | B1 | 平均評価値が2.75以上3.5未満 |
| 関連職種 | B2 | 守備範囲の職種のジャンルと関連表で結ばれており、自身の平均評価値が2.75未満 |

平均評価値はS1〜S4の平均である。4スロットの平均は0.25刻みになるため、判定値2.75は、4スロットの合計が11以上であることを示す。判定値3.5は、4スロットの合計が14以上であることを示す。2.75以上は職種名を見習いとして示せる入口の水準、3.5以上は職種名を守備範囲として示せる水準として扱う。共通の値の扱いと対応する。

根拠の箇条書きは以下を挙げる。

1. 守備範囲の職種は、そのジャンルの平均評価値
2. 見習い職種は、そのジャンルの平均評価値
3. 関連職種は、結ばれている相手のジャンル名と、関連表が記す関連の根拠

同じグループに属することは関連職種の根拠にしない。グループは表の見出しであり、ジャンルどうしの近さを表さないため。

工程から算出する役割は対応可能なポジションが扱う。本節はジャンルから算出する分野の名前だけを扱う。

### 5.8. 対応可能なポジション

B1の主となる出力。工程の平均評価値と汎用能力をもとに、いま説明できる役割と、次に届きそうな役割を示す。
職種名は業務ジャンルから算出する分野名であり、対応可能なポジションは工程と汎用能力から算出する役割名である。
このカードは職種適性や配属適性を判定するものではない。

| 項目 | 内容 |
| --- | --- |
| 目的 | B1を満たす |
| 入力 | `procAvg`、`categoryAvg` |
| 算出条件 | 工程の平均評価値と汎用能力カテゴリの平均評価値を使い、ポジションごとの状態を「満たしている」「満たしそう」「未到達」に分類する |
| 表示内容 | 全ポジションをグループ別に表示し、状態で塗り分ける。各ポジションには根拠を表示する。工程の平均評価値表、汎用能力カテゴリの平均評価値表も表示する |
| 表示順 | 基礎ポジション、応用ポジション、発展ポジションの順。同一グループ内は本節の定義順 |
| 空状態 | 全ポジションを表示するため、ポジション名の空状態はない。すべて未到達の場合も、工程の平均評価値表と汎用能力カテゴリの平均評価値表を表示する |
| 根拠表示 | 満たしている条件、満たしそうな条件、未到達の条件を表示する |
| 表示しない内容 | 順位、適合度％、おすすめ順、他者比較 |

ポジション名の出力枠は必ず置く。
条件を満たしたポジションだけを列挙すると、回答者が候補全体の中でどこにいるか分からない。
そのため、対象にする全ポジションを常に表示し、状態で塗り分ける。

ポジションは段階の異なる3グループに分ける。
グループ名は画面にも表示する。

| グループ | 定義 |
| --- | --- |
| 基礎ポジション | 実装、テスト、運用など、単一の実行工程の担当範囲から判定するポジション |
| 応用ポジション | 複数工程の担当範囲、または土台にするポジションと汎用能力カテゴリの高さから判定するポジション |
| 発展ポジション | 土台にするポジションと、複数の汎用能力カテゴリの高さを組み合わせて判定するポジション |

状態は以下の3つとする。

| 状態 | 意味 | 表示 |
| --- | --- | --- |
| 満たしている | ポジションの全条件を満たしている | 濃い塗り |
| 満たしそう | 全条件のうち未達のものが近接範囲に収まっている | 薄い塗り |
| 未到達 | 上記以外 | 無地 |

近接範囲は、各しきい値の0.5以内の不足までとする。
しきい値3.0の条件は2.5以上3.0未満、しきい値3.5の条件は3.0以上3.5未満、しきい値4.0の条件は3.5以上4.0未満を「満たしそう」とする。
複数条件を持つポジションは、すべての条件が「満たしている」または「満たしそう」で、かつ少なくとも1つが「満たしそう」の場合に、ポジション全体を「満たしそう」とする。
いずれかの条件が近接範囲にも届かない場合は、ポジション全体を「未到達」とする。

「要件定義または詳細設計」のようなOR条件は、どちらか一方が満たしていれば「満たしている」とする。
どちらも満たしていないが、どちらか一方が近接範囲に入っていれば「満たしそう」とする。
土台にするポジションがある場合、土台の状態も条件として扱う。

基礎ポジションの判定条件は以下のとおり。

| グループ | ポジション | 判定条件 |
| --- | --- | --- |
| 基礎ポジション | プログラマー | 実装が3.0以上 |
| 基礎ポジション | テスター・QA | テストが3.0以上 |
| 基礎ポジション | 運用担当 | 運用・保守が3.0以上 |

応用ポジションと発展ポジションは、土台にするポジションの状態と、汎用能力カテゴリの条件を組み合わせて判定する。
ただし、システムエンジニアは複数工程の担当範囲から判定するため、基礎ポジションを土台にしない。
土台の条件は応用ポジションおよび発展ポジション側に書き直さない。土台の状態を参照する。

| グループ | ポジション | 土台 | 条件 |
| --- | --- | --- | --- |
| 応用ポジション | システムエンジニア | なし | 基本設計が3.0以上、かつ要件定義または詳細設計が3.0以上 |
| 応用ポジション | アーキテクト | システムエンジニア | 設計力が4.0以上、技術判断と基盤構築が3.5以上 |
| 応用ポジション | テックリード | プログラマー | 実装力が4.0以上、技術判断と基盤構築が3.5以上 |
| 応用ポジション | プロジェクトリーダー | プログラマーまたはシステムエンジニア | プロジェクト運営が3.5以上 |
| 発展ポジション | システムコンサルタント | システムエンジニア | 業務理解と価値判断が4.0以上、プロジェクト運営が3.5以上、技術判断と基盤構築が3.5以上 |
| 発展ポジション | プロジェクトマネージャー | システムエンジニア | プロジェクト運営が4.0以上、業務理解と価値判断が3.5以上 |
| 発展ポジション | プロダクトマネージャー | システムエンジニア | 業務理解と価値判断が4.0以上、プロジェクト運営が3.5以上、技術判断と基盤構築が3.5以上 |

4.0以上は、そのポジションの主軸となる能力として扱う。3.5以上は、主軸を支える能力として扱う。

### 5.9. 課題・改善内容

経験はあるが、まだ低い項目を示す。

| 項目 | 内容 |
| --- | --- |
| 目的 | B3を満たす |
| 入力 | `genres`、`procs`、`gens` |
| 算出条件 | 個別値が2または3の項目を抽出する。値1は対象外とする |
| 表示内容 | 業務ジャンル、工程、汎用能力の3ブロックに分け、ジャンル名とスロット名、工程名と観点名、カテゴリ名と設問名をすべて表示する |
| 表示順 | ブロック1、ブロック2、ブロック3の順。各ブロック内は定義順 |
| 空状態 | 該当項目がない場合は該当なしとして表示する |
| 根拠表示 | 各項目の評価値を表示する |
| 表示しない内容 | 値1の項目、値4〜5の項目 |

3ブロックすべてを元データにする。汎用能力は分野や工程が変わっても今の仕事の中で深掘りできるため、この出力の打ち手に最も合う。

守備範囲マップの隣接とは別の概念である。両方を表示する。

| 表示 | 意味 | 打ち手 |
| --- | --- | --- |
| 課題・改善内容 | 経験はあるが評価が低い | 今の仕事の中で深掘りする |
| 隣接 | 未経験だが守備範囲に接している | 経験機会そのものを取りに行く |

### 5.11. ジャンルの関連表

ジャンルどうしの近さを定める。守備範囲マップの行の隣接と、関連職種が使う。

関連とは、同じ案件の中で隣り合って現れることである。技術が共通することではない。
関連するジャンルは主戦場と異なる技術を要するため、S1〜S4が一致しないことは関連を否定しない。
スロットが重なるほど同じ業務に近づき、別のジャンルとして分けている意味が薄れる。

関連とみなすのは、次のいずれかを満たすペアである。

1. 同じシステムを構成する層として直接つながる
2. 同じ案件の中で、別の担当者に割り当てられることが多い
3. 一方の成果物が、もう一方の入力になる

関連に方向は持たせない。どちらのジャンルから見ても関連とする。

## 6. データ仕様

### 6.1. JSON出力

入力値のみを保存する。分析結果は含めない。

```json
{
  "schemaVersion": "1.1",
  "exportedAt": "2026-08-05T10:00:00+09:00",
  "profile": {
    "name": "メイテック 太郎",
    "employeeNo": "12345678",
    "department": "横浜西EC",
    "specialty": "IT",
    "experienceYears": "4-9"
  },
  "genres": {
    "web-frontend": { "s1": 4, "s2": 4, "s3": 3, "s4": 3 },
    "desktop-app": { "s1": 3, "s2": 3, "s3": 2, "s4": 2 }
  },
  "processes": {
    "requirements": { "1": 3, "2": 3, "3": 2, "4": 3 },
    "implementation": { "1": 5, "2": 4, "3": 4, "4": 3 }
  },
  "generalSkills": {
    "design": { "1": 4, "2": 4, "3": 3, "4": 3 }
  }
}
```

| キー | 保存する値 |
| --- | --- |
| `profile` | 基本情報 |
| `genres` | 業務ジャンルの全スロット値 |
| `processes` | 工程能力の全観点値 |
| `generalSkills` | 汎用能力の全設問値 |

| 規則 | 内容 |
| --- | --- |
| 未回答 | 値1として出力する。未経験と同じ扱いのため区別しない |
| 出力範囲 | 全設問を出力する。省略しない |
| キー | 表示名ではなく固定ID |

### 6.2. JSON読み込み

| 項目 | 内容 |
| --- | --- |
| 対象 | 6.1 の形式のJSONファイル |
| 読み込み後 | 入力画面に反映し、再編集できる |
| 分析 | 読み込み時点のロジックで再計算する |

### 6.3. スキーマ互換性

| 状況 | 動作 |
| --- | --- |
| schemaVersion が古い | 読み込む |
| 存在しないIDが含まれる | 無視する |
| 新設されたIDが含まれない | 値1（未経験）として扱う |
| schemaVersion がない | 読み込みを中止し、その旨を表示する |

## 7. 画面仕様

### 7.1. 画面全体

入力画面と結果画面を持つ。
入力画面で回答した内容から、結果画面を生成する。

### 7.2. 入力画面

1. ブロックごとにカードで区切る
2. 業務ジャンルと工程はアコーディオンで表示する。折りたたみ時も代表技術または観点の要約を並べる
3. 汎用能力もカテゴリ単位のアコーディオンで表示する
4. 各設問は5択のラジオボタン。選択肢の表示ラベルはそのブロックのアンカーの表示ラベルを使う
5. 同じ設問内の5つの選択肢は等幅で表示する。文章量によってボタン幅が変わらないようにする
6. 初期状態は未選択とする
7. 業務ジャンルは初期状態で折りたたむ。工程能力と汎用能力は全員が回答するため、アコーディオンを初期状態で開く
8. JSONの読み込みと出力のボタンを置く

### 7.3. 結果画面

結果カードの表示順序は以下のとおり。

1. 守備範囲マップ
2. 汎用能力（カテゴリ別のレーダーチャート）
3. 職種名（守備範囲の職種、見習い職種、関連職種）
4. 対応可能なポジション
5. 課題・改善内容
6. 明細表

見出しには出力の内容の名前を使う。図の種類を見出しにしない。

強みは別枠で表示しない。

### 7.4. 操作

| 操作 | 内容 |
| --- | --- |
| JSON読み込み | 保存済みJSONを読み込み、入力画面へ反映する |
| JSON出力 | 現在の入力値をJSONとして出力する |
| 再計算 | 入力値の変更後、現在のロジックで結果を再計算する |
