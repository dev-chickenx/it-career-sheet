# エンジニア キャリアプランシート 要求仕様書

## 1. この資料について

キャリアプランシートに対する要求を一元管理する。何を求められ、それをどう扱ったかを記録する。
仕様書（02_仕様書.md）が「何を作るか」を定めるのに対し、本書は「なぜそうなっているか」を保持する。

| 章 | 内容 |
| --- | --- |
| 2 | 記載ルール |
| 3 | 目的から導出した要求 |
| 4 | 打合せから起票した要求 |
| 5 | レビューから起票した要求 |
| 6 | 保留・見送りの一覧 |

## 2. 記載ルール

要求は REQ-nnn で識別する。番号は再利用しない。

| 項目 | 内容 |
| --- | --- |
| 出所 | 目的／議事録（日付）／レビュー |
| 実現性 | 可／条件付き可／不可 |
| 状態 | 反映済／保留／見送り |
| 反映先 | 仕様書の章番号。見送りの場合は理由を書いた章 |

状態が「反映済」であっても、仕様が確定したという意味ではない。未確定の値やロジックは本書6章で管理する。

## 3. 目的から導出した要求

### REQ-001 自分の現在地を言語化できること

- 出所：目的
- 要求：回答者が、自分がどの分野のどの工程までできるかを言葉にできる状態にする
- 実現性：可
- 難所：単一の指標では表現できない。分野と工程の2軸が必要
- 対応方針：
  1. 業務ジャンルと工程の2軸で守備範囲を表す
  2. 目的を恩恵 B1〜B4 に分解し、分析はこの4つを満たすために行う
  3. 職種は結果に付くラベルとして扱う
- 反映先：2.2、3.1、5.2
- 状態：反映済

### REQ-002 全回答者が自分を写せること

- 出所：目的
- 要求：どの分野のエンジニアが回答しても、自分の経験を記入できるようにする
- 実現性：条件付き可
- 難所：現行シートはWeb系5ジャンルしか持たず、IT分野の網羅率が28%だった
- 対応方針：
  1. IT分野を18ジャンルに整理し、網羅率を100%にする
  2. MS分野は対象外とし、v2で扱う
- 反映先：4.2
- 状態：反映済

### REQ-003 順位や等級で評価しないこと

- 出所：目的
- 要求：総合評価、等級、適合度％、順位を出さない
- 実現性：可
- 難所：依頼元から「推奨職種を算出したい」という要望があり、衝突する
- 対応方針：職種名は出すが、順位と数値は付けない。根拠は 03_エビデンス編.md
- 反映先：2.4、5.4、5.5
- 状態：反映済

### REQ-004 自己評価の精度を担保すること

- 出所：レビュー（エビデンス調査）
- 要求：順位や比較を出さない場合でも、回答者が判断できる基準を与える
- 実現性：可
- 難所：自己評価と客観指標の相関は平均0.29と低い。規範的基準がないと精度が出ない
- 対応方針：アンカーを規範的基準として機能させる。各段の意味を外部から定義する
- 反映先：3.4
- 状態：反映済

### REQ-005 設問の粒度を揃えること

- 出所：目的
- 要求：同一カテゴリ内の設問が同じ抽象度で並ぶようにする
- 実現性：可
- 難所：現行シートは言語・ライブラリ・製品・ツールが同じ列に混在していた
- 対応方針：
  1. 設計ルール4条を定め、3ブロックに分離する
  2. 個別技術はジャンルのスロットに降ろす
- 反映先：2.5、3.2
- 状態：反映済

## 4. 打合せから起票した要求

出所はすべて 2026年8月4日の打合せ（docs/minutes/20260804_打合せ議事録.md）。

### REQ-101 業務ジャンルにシステムコンサルを追加

- 要求：業務分析、システム構想、全体アーキテクチャ設計を扱う「システムコンサル」をジャンルに追加する
- 実現性：不可
- 難所：ジャンルは4スロット（主要言語、主要フレームワーク、設計様式、実行環境）で測る。システムコンサルは3つが埋まらず、レーダーが成立しない
- 対応方針：
  1. ジャンルには追加しない
  2. REQ-102 と REQ-108 で意図を満たす
- 反映先：なし（見送り。理由は本項目に記載）
- 状態：見送り

### REQ-102 要件定義に業務分析系の観点を追加

- 要求：要件定義に次の3観点を追加する
  1. 現行業務の分析
  2. 現在の課題の特定
  3. システム化方針の立案
- 実現性：可
- 難所：既存観点「業務・現行システムの理解」と重なる
- 対応方針：既存観点を「現行業務・現行システムの分析」に改称して統合し、8観点に拡張する
- 反映先：4.3.1
- 状態：反映済

### REQ-103 全体アーキテクチャ設計を工程に追加

- 要求：工程に全体アーキテクチャ設計を追加する
- 実現性：可（対応不要）
- 難所：なし
- 対応方針：基本設計の観点1「システム全体構成の決定」に含まれるため追加しない
- 反映先：4.3.2
- 状態：反映済

### REQ-104 汎用能力のカテゴリ数を各グループ5件に揃える

- 要求：G1・G2・G3 のカテゴリ数を5件に揃える
- 実現性：条件付き可
- 難所：5件に揃えると2つの問題が生じる
  1. G3 に3カテゴリを新設する必要があり、枠を埋めるためのカテゴリが混じる
  2. 観点を3件に減らす必要があり、カテゴリ名に対して中身が薄くなる
- 対応方針：各4カテゴリ × 4観点に変更する。レーダーの軸は4から6の範囲であれば読めるため、5である必然性がない
- 反映先：4.4
- 状態：反映済（内容を変更）

### REQ-105 汎用能力の設問数を減らす

- 要求：汎用能力の設問が多すぎる
- 実現性：可
- 難所：カテゴリを増やしながら設問を減らす必要がある
- 対応方針：カテゴリを11から12にしつつ、観点を各4件に固定する。58問から48問に減
- 反映先：4.4、4.6
- 状態：反映済

### REQ-106 G1にカテゴリを1件追加

- 要求：G1 に入力項目を1件追加する
- 実現性：可
- 難所：なし
- 対応方針：
  1. G1-4 データ操作・永続化 を新設する
  2. コード理解とデバッグを G1-2 に統合し、4カテゴリに整理する
- 反映先：4.4.1
- 状態：反映済

### REQ-107 G3にカテゴリを3件追加

- 要求：G3 に入力項目を3件追加する
- 実現性：条件付き可
- 難所：3件追加すると5カテゴリになり、REQ-104 の判断と衝突する
- 対応方針：
  1. G3-3 顧客・ステークホルダー対応、G3-4 セルフマネジメントの2件を新設する
  2. 育成は G3-2 の観点に含める
- 反映先：4.4.3
- 状態：反映済（件数を変更）

### REQ-108 守備範囲にシステムコンサルを追加

- 要求：守備範囲にシステムコンサルを追加する
- 実現性：条件付き可
- 難所：守備範囲マップの縦軸は業務ジャンルであり、職種ではない
- 対応方針：対応可能なポジションの判定条件に「システムコンサルタント」を追加する
- 反映先：5.5
- 状態：反映済（実現手段を変更）

### REQ-109 レーダーをG1・G2・G3の3枚にする

- 要求：レーダーをG1・G2・G3の粒度で表示し、各5項目の軸にする
- 実現性：条件付き可
- 難所：軸数は REQ-104 の結論に依存する
- 対応方針：
  1. レーダーを3枚にする
  2. 各レーダーの軸は4項目とする
- 反映先：5.3
- 状態：反映済（軸数を変更）

### REQ-110 強みの別枠表示を廃止

- 要求：関連職種とポジションに理由を箇条書きで記載するため、強みの別枠は不要
- 実現性：可
- 難所：職種にもポジションにも紐づかない高評価の観点が出力から消える懸念があった
- 対応方針：廃止する。汎用能力のレーダー3枚が全カテゴリを表示し、守備範囲マップのバーが重み付けを表示するため、情報は失われない
- 反映先：7.2
- 状態：反映済

### REQ-111 「伸びしろ」の改称と抽出条件の定義

- 要求：「伸びしろ」を「課題」や「改善内容」に改称し、未回答を除いて評価値が低いものを抽出する
- 実現性：可
- 難所：未回答と未経験を区別する必要があるかが不明確だった
- 対応方針：
  1. 未回答は未経験と同じ扱いとし、値1とする
  2. 課題は値2と3を対象とする
  3. 値1のうち守備範囲に接するものは隣接として別に表示する
- 反映先：5.1、5.6
- 状態：反映済

### REQ-112 関連職種を業務ジャンルの重み付けから算出

- 要求：業務ジャンルの重み付けをもとに、該当する職種を算出する
- 実現性：条件付き可
- 難所：ジャンルと職種の対応表が存在しない
- 対応方針：
  1. 18ジャンルそれぞれに職種名を割り当てた対応表を作成する
  2. 表示件数は実データを見てから決める。閾値の採用根拠はREQ-222にある
- 反映先：5.4、5.7
- 状態：反映済（閾値の採用根拠はREQ-222を参照）

### REQ-113 対応可能なポジションを工程の重み付けから算出

- 要求：工程の重み付けをもとに、プロジェクトにおける役割が分かる文言で表示する
- 実現性：条件付き可
- 難所：
  1. 判定条件が存在しない
  2. 工程だけでは判定できないポジションがある
- 対応方針：
  1. 8ポジションの判定条件を暫定で定義する
  2. 一部は汎用能力のカテゴリを条件に含める
  3. 展開後に調整する
- 反映先：5.5
- 状態：反映済（条件は暫定）

### REQ-114 入力結果をJSONで出力

- 要求：入力結果をJSONで出力可能にする
- 実現性：可
- 難所：設問名をキーにすると、設問名の変更で過去データが読めなくなる
- 対応方針：表示名とは独立した固定IDを付与し、それをキーにする
- 反映先：3.5、6.1
- 状態：反映済

### REQ-115 JSONを読み込んで過去の入力と分析結果を表示

- 要求：出力した結果を読み込むことで、過去の入力内容と分析結果を表示できるようにする
- 実現性：可
- 難所：分析結果を保存すると、ロジック変更後に過去データを再評価できない
- 対応方針：分析結果は保存しない。入力値のみを保存し、読み込み時点のロジックで再計算する
- 反映先：6.1、6.2、6.3
- 状態：反映済

## 5. レビューから起票した要求

### REQ-201 工程「実装」の観点を成立させる

- 出所：レビュー
- 要求：工程「実装」の観点が評価として機能していない
- 実現性：可
- 難所：実装の行為は「コードを書く」ほぼ一つで、他の観点は汎用能力と重複する
- 対応方針：
  1. 実装対象の種類（新規機能、既存改修、共通部品）で分ける
  2. 「コーディング（規約準拠）」は全員が4以上になり差がつかないため廃止する
- 反映先：4.3.4
- 状態：反映済

### REQ-202 守備範囲マップで工程の習熟度が読めるようにする

- 出所：レビュー
- 要求：工程ができていても、回答済みジャンルとの交点しか塗られず、できていないように見える
- 実現性：可
- 難所：工程を1回しか聞かないため、マップのセルは行と列の情報の積でしかない
- 対応方針：
  1. 有効な工程は列全体、有効なジャンルは行全体に色を付ける
  2. 習熟度をバーで併記する
- 反映先：5.2
- 状態：反映済

### REQ-203 ジャンルのグループ単位の近さを表現する

### REQ-207 天井効果が出た観点の書き換え基準

- 出所：レビュー（要件確定 2026-08-09）
- 要求：旧仕様書8.1 #6、天井効果が出た観点の書き換えの判断基準を決める
- 実現性：可
- 難所：実際にどの観点が天井効果に該当するかは回答データがないと分からない

  3. 20件・80%は暫定値であり、運用開始後の最初の見直しで調整してよい
- 反映先：なし（運用ルールとして本項目に記載）

### REQ-208 迷いの多かった観点へのアンカー文言追加基準

- 出所：レビュー（要件確定 2026-08-09）

- 反映先：なし（運用ルールとして本項目に記載）

### REQ-209 関連職種の算出をB2に合わせる
