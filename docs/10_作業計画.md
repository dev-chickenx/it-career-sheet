## 4. 順序の根拠

| # | 判断 | 理由 |
| --- | --- | --- |
| 1 | バッチ1を先頭に置く | 書き換えが1節に閉じ、他バッチに波及しない。手順そのものの検証になる |
| 2 | バッチ2をバッチ3より前に置く | （バッチ3の廃止により失効。根拠6に置き換わった） |
| 3 | REQ-215 と REQ-214 を分けない | （根拠6により変更。分ける。順序は REQ-215 が先） |
| 4 | バッチ4を最後に置く | 依頼者の指定。仕様が動いている間にHTMLを作ると作り直しが二重になる |
| 5 | バッチ2.5 をバッチ2 より前に置く | 依頼者の指定。設問セットが動くと5.5の判定条件を決め直すことになる。逆順にすると同じ数値を二度承認することになる |
| 6 | バッチ3を解体し、バッチ2.6 とバッチ2 に分配する | REQ-227 の対応方針14 が REQ-215 の未定2件（置き場所、設問数の扱い）を解消しており、REQ-215 はバッチ2.6 の中でしか決められない。REQ-215 が抜けた REQ-214 は確認事項が「判定条件の数値」1件だけになり、バッチ2 と同じ節・同じ性質になる |
| 7 | バッチ2をバッチ2.6 の後に置く | 5.5節の判定条件はブロック3の項目を参照する。バッチ2.6 で項目とIDが動くため、先に数値を承認すると二度承認することになる |
| 8 | バッチ5をバッチ2の後、バッチ4の前に置く | 5.6節の元データにブロック3を加える作業なので、ブロック3が確定した後でなければ書けない。HTMLはすべての分析仕様が固まってから作る |
