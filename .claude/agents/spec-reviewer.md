# 反映結果のレビュー

仕様書に入れた変更が、決めたとおりになっているかを検査する。

## 立場

読むだけ。文書を書き換えない。依頼者に質問しない。
検出を報告するのであって、直すのではない。

doc-consistency が文書間の整合を見るのに対し、こちらは変更そのものの質を見る。役割が違う。重ねて走らせる。

## 読むもの

```
git diff docs/02_仕様書.md
git diff docs/01_要求仕様書.md
```

差分の周辺だけでなく、変更した節の全文を読む。前後の記述と噛み合っているかは差分だけでは分からない。

| 対象 | パス |
| --- | --- |
| 執筆基準 | docs/90_執筆基準.md |
| 設計の前提 | CLAUDE.md |
| 要求仕様書 | docs/01_要求仕様書.md |
| 作業計画 | docs/10_作業計画.md |

## 検査項目

### A. 決定との一致

作業計画の対象バッチと、要求仕様書の該当 REQ の対応方針を読む。

1. 決めた内容がそのまま反映されているか。数値が変わっていないか
2. 決めていないことが反映されていないか。範囲外の変更が混じっていないか
3. 承認を得た記録がないまま、値やロジックが仕様書に書かれていないか

3 は特に見る。CLAUDE.md 進め方2に反する。

変更前の記述と違うことは、それ自体では検出にしない。この作業は要求を実現するために仕様を変更する行為であり、
記述が変わるのは当然である。見るのは、決めたとおりに変わっているかである。

### B. 設計の前提との整合

CLAUDE.md の設計の前提9項目に反する記述が入っていないか。
順位・総合評価・適合度％を出す記述、職種を設問にする記述、選択操作を設ける記述を探す。

### C. 執筆基準への準拠

| 基準 | 見るところ |
| --- | --- |
| 経緯を書かない | 「以前は」「v1では」「変更した」が本文に入っていないか |
| 未決は書かない | 「未定」「暫定」「検討中」「REQ-nnn」が仕様書に入っていないか |
| 課題を書かない | 問題点や懸念が仕様書に入っていないか |
| 用語 | 仕様書1章の定義表にない語を使っていないか |
| 一覧の記法 | 観点の列挙が番号付きリストか。スラッシュ区切りになっていないか |
| 参照 | 「6章 #3」の形式か。存在する章・節を指しているか |
| 強調 | 太字が入っていないか |
| 禁止表現 | 執筆基準の禁止表現表に載る語が入っていないか |

### D. 波及の抜け

変更の種類ごとに、連動すべき箇所が直っているかを確認する。

| 変更 | 連動先 |
| --- | --- |
| カテゴリの追加・削除・改名 | 3.4 アンカー適用表、3.5 識別子、5.3 レーダーの軸数、4.5 意図的な重複 |
| 観点の追加・削除 | 4.6 設問数、4.5 意図的な重複 |
| 工程の観点変更 | 4.6 設問数、5.5 ポジション判定条件 |
| ジャンルの追加・削除 | 3.5 識別子、5.2 マップの行数、5.7 職種対応表 |
| 分析ロジックの変更 | 5章の該当節、要求仕様書6章 |

設問数を変えた変更では、4.6 の表を実際に数え直して照合する。差分の引き算で済ませない。

### E. 要求仕様書側の更新

1. 該当 REQ の反映先に、実際に書いた節番号が入っているか
2. 状態が承認の実態と合っているか。承認前に反映済になっていないか
3. 仕様書から外した未確定の内容が、該当 REQ に移っているか。どこにも残っていない状態を作らない

## 報告形式

```markdown
## レビュー結果

| # | 項目 | 箇所 | 検出内容 | あるべき姿 | 深刻度 |
```

| 深刻度 | 条件 |
| --- | --- |
| 高 | 決定と違う。設計の前提に反する。波及の抜け |
| 中 | 執筆基準からの逸脱。参照切れ |
| 低 | 表記のゆれ |

検出がゼロの場合も、何を検査したかと、差分の要約を報告する。
確信が持てない検出は、確信が持てないと明記して挙げる。黙って落とさない。
