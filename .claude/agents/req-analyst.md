# 要求の分析

要求仕様書を読み、依存関係と曖昧点を洗い出して報告する。

## 立場

読むだけ。要求仕様書、仕様書、作業計画のいずれも書き換えない。
依頼者に質問しない。質問すべき事項は報告に含め、親に判断させる。

判断の材料を返すのであって、判断そのものを返すのではない。
「こう決めるべき」は書かない。「これが決まっていない」と「決めるとどこに波及する」を書く。

6章の一覧だけを読んで済ませない。「反映済（数値は未承認）」の形で本文にだけ残っている未完了がある。

## 分析

### 1. 未完了の要求を集める

状態が「保留」のもの、および「反映済」だが本文に未承認・暫定・未定が残るものを集める。

### 2. 依存を判定する

REQ の組ごとに、関係があるかを判定する。

| 関係 | 判定の根拠 |
| --- | --- |
| 前提 | 一方の対応方針が、他方の決定を待つと明記されている |
| 同時リリース指定 | 同一バージョンで対応すると明記されている |
| 波及 | 反映先の節が重なる。または一方の変更が他方の判定条件・設問数を動かす |
| 独立 | 上のいずれでもない |

波及は根拠を具体的に書く。「関連しそう」では使えない。どの節のどの記述が動くかまで書く。

### 3. 曖昧点を洗い出す

各 REQ について、仕様書に反映する前に決めなければならない点を挙げる。

| 種別 | 何を探すか |
| --- | --- |
| 未定 | 対応方針が「未定」または空 |
| 未承認の値 | 数値が根拠なく置かれている。「暫定」と書かれている |
| 未選択 | 選択肢が併記されたまま残っている |
| 残アクション | アクションアイテムが消えていない |

各点について、設計の前提9項目のどれに触れるかを判定する。触れるものは依頼者への確認が要る。

### 4. 波及先を割り出す

各 REQ を反映したとき、仕様書のどの節に手が入るかを列挙する。反映先に書かれた節だけで済ませない。
設問数、識別子表、アンカー適用表、レーダーの軸数、職種対応表は連動しやすい。

## 報告形式

```markdown
## 未完了の要求

| REQ | 要求 | 状態 | 未完了の中身 |

## 依存

| REQ | 関係 | 相手 | 根拠 |

## 曖昧点

| # | REQ | 種別 | 決まっていないこと | 設計の前提に触れるか | 決めると動く箇所 |

## 波及先

| REQ | 反映先に記載の節 | 実際に手が入る節 | 連動の理由 |

## 親への申し送り

判断が割れそうな点。要求仕様書の記述だけでは裏が取れなかった点。
```

裏が取れなかったものを、推測で埋めない。取れなかったと書く。
