# バッチの計画

要求仕様書6章の保留 REQ を棚卸しし、一度に反映する単位に束ねて順序を決める。

## 前提

仕様書は書き換えない。要求仕様書も書き換えない。書くのは作業計画だけ。

## 手順

### 1. 残りを数える

要求仕様書6章の一覧と各 REQ 本体の状態を突き合わせる。両方を見る。一覧だけでは漏れる。

| 状態 | 扱い |
| --- | --- |
| 保留 | バッチに載せる |
| 見送り | 載せない。v2 の候補として末尾に一覧で残す |
| 反映済 | 載せない |
| 反映済だが数値が未承認 | 載せる。承認が済むまで未完 |

「反映済（数値は未承認）」の形で残っているものを見落としやすい。本文の状態欄を全件読む。

### 2. 依存を調べる

REQ 間の関係は3種類ある。混同しない。

| 関係 | 意味 | 束ね方 |
| --- | --- | --- |
| 前提 | Aが決まらないとBを決められない | 同じバッチ。または A を先のバッチに置く |
| 同時リリース指定 | 片方だけ反映すると仕様が中途半端になる | 必ず同じバッチ |
| 波及 | Aを反映するとBの記述に手が入る | 別バッチでよい。順序だけ決める |

分量が多い、または REQ 本体の記述が長い場合は req-analyst エージェントに依存の洗い出しを任せる。
返ってきた依存関係はそのまま採用せず、要求仕様書の本文で裏を取る。

### 3. 束ねる

1バッチの上限を守る。レビュー1回で見きれる量に収めるため。

| 項目 | 上限 |
| --- | --- |
| REQ の件数 | 3件 |
| 書き換える仕様書の節 | 3節 |
| 依頼者に確認する事項 | 4件 |

束ねる条件は以下のいずれか。

1. 前提関係または同時リリース指定がある
2. 同じ節を書き換える
3. 同じ性質の判断で、1回の確認にまとめられる

分ける条件は以下のいずれか。当てはまれば束ねない。

1. レビューの観点が違う（設問の増減と、分析ロジックの数値は別物）
2. 片方が差し戻されたとき、もう片方まで巻き戻る
3. 上限のどれかを超える

確認事項が4件を超える REQ は、単独で1バッチにする。バッチ内で確認を2回に分ける。
REQ そのものを分割しない。番号の管理が壊れる。

### 4. 順序を決める

手戻りが少ない順に並べる。判断の基準は以下。

| 優先 | 理由 |
| --- | --- |
| 他のバッチに波及するもの | 後にすると前のバッチを書き直すことになる |
| 影響範囲が狭いもの | 手順そのものの検証になる。最初のバッチに向く |
| 前提が揃っているもの | 未定の前提を持つバッチを先に置くと止まる |

波及の向きが双方向のときは、波及の量が少ない側を先に置く。

### 5. 作業計画に書く

`docs/10_作業計画.md` を更新する。書式は同ファイルの既存バッチに合わせる。

各バッチに以下を持たせる。

| 項目 | 内容 |
| --- | --- |
| 対象 REQ | 番号と要求の要約 |
| 束ねた理由 | どの条件に当てはまるか |
| 書き換える節 | 仕様書の節番号 |
| 確認事項 | P1 で依頼者に聞くこと。この時点では見出しだけでよい |
| 状態 | 未着手／進行中／反映済 |

順序を変えたときは、変えた理由を1行で残す。

### 6. 次のバッチを指す

「現在地」の対象バッチを、未着手のうち先頭のものにする。フェーズを P1 にする。

## やらないこと

1. 保留の REQ を作業計画に載せないまま放置しない。扱わないなら見送りに変える
2. バッチの中で REQ を分割しない
3. 束ねた理由を書かずに束ねない。差戻し時にバッチを組み直せなくなる
4. 作業計画に仕様の中身を書かない。節番号への参照に留める
