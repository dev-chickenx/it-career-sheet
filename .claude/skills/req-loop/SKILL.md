# 反復の入口

残った要求を、一度に1バッチだけ仕様書に反映する。反映のたびに依頼者のレビューを挟む。

このスキル自体は文書を書き換えない。作業計画のフェーズを読み、対応する手順へ渡すだけ。

## この反復が何をするものか

**要求を実現するために仕様を変更する。**仕様書は変更の対象であって、変更を止める根拠ではない。

「仕様書にこう書いてあるから」を理由に、要求の実現を狭めたり断ったりしない。
現在の記述と要求が衝突したら、変えるのは記述のほうである。変えられない理由は、
仕様書ではなく CLAUDE.md の設計の前提か、依頼者の決定に求める。

仕様書には現在の仕様だけを書く。未確定の値、暫定のロジック、REQ 番号、課題は書かない。
これらは仕様ではないので、要求仕様書に置く。

## 状態の置き場

`docs/10_作業計画.md` が唯一の状態。会話の記憶に頼らない。
セッションが切れても、このファイルを読めば続きから再開できる。

確定した内容は要求仕様書と仕様書に書く。作業計画には作業の進行だけを持つ。

## フェーズ

| ID | フェーズ | 完了の条件 | 渡す先 |
| --- | --- | --- | --- |
| P0 | 計画 | 次に着手するバッチが1つ決まっている | req-backlog |
| P1 | 精査 | バッチ内の曖昧点が消え、決定が要求仕様書に書かれている | req-clarify |
| P2 | 反映 | 仕様書の該当節と波及箇所が更新されている | spec-update |
| P3 | 検査 | 整合の検出結果がゼロ、または残す理由が書かれている | doc-consistency |
| P4 | レビュー | 依頼者が承認、または差戻しの内容を示している | spec-handoff |
| P5 | 締め | REQ の状態と仕様書の版番号が更新されている | spec-handoff |

P5 の次は P0 に戻る。保留の REQ が尽きたらループを終える。

## 人の入力で止まる地点

2つだけ。ここ以外で依頼者に問いかけない。

| 地点 | 何を聞くか |
| --- | --- |
| P1 の末尾 | バッチ内の曖昧点。暫定値の承認。最低1問 |
| P4 | 反映結果でよいか。承認または差戻し |

P0・P2・P3・P5 は判断を自分で行う。判断できない点が出たら、それは P1 で聞き漏らしている。P1 に戻す。

## 1回の実行

### 1. 現在地を読む

`docs/10_作業計画.md` の「現在地」を読む。ファイルがなければ P0 として扱う。

作業計画のフェーズと作業ツリーの実態がずれることがある。以下を照合し、実態を優先する。

| 記載 | 実態の確認 | ずれていたとき |
| --- | --- | --- |
| P2 反映 | `git diff docs/02_仕様書.md` に変更がある | 変更がなければ P2 の先頭から |
| P4 レビュー | 対象バッチの REQ が要求仕様書でまだ保留 | 反映済ならフェーズを P0 に戻す |

### 2. フェーズの手順を実行する

フェーズ表の「渡す先」のスキルを Skill ツールで呼ぶ。自分で手順を再現しない。

1周で複数フェーズを進めてよい。P1 の Ask、または P4 の提示に到達したらそこで止める。

### 3. 現在地を書き戻す

止まった時点のフェーズを作業計画に書く。何をしたかを1行で残す。

## 差戻しの戻り先

P4 で依頼者が差し戻したとき、内容によって戻り先が変わる。

| 差戻しの内容 | 戻り先 |
| --- | --- |
| 決定そのものが違う（値、方針） | P1。決定を取り消し、聞き直す |
| 決定は合っているが仕様書の書き方が悪い | P2 |
| 反映漏れ、波及箇所の抜け | P2 |
| このバッチの束ね方が悪い | P0。バッチを組み直す |

戻る前に、差戻しの内容を作業計画のバッチに1行で記録する。同じ指摘を2度受けないため。

## ループの終わり

要求仕様書6章に状態「保留」の REQ がなくなったら終える。
「見送り」は対象にしない。v2 で扱うものは作業計画に載せない。

終えるときは、残った見送り・v2 送りの一覧を報告する。

## やらないこと

1. 1周で2バッチ以上を反映しない。レビュー1回で見きれる量を超える
2. P1 を飛ばして P2 に進まない。曖昧なまま反映すると差戻しがバッチ全体に及ぶ
3. 依頼者の承認前に REQ の状態を反映済にしない
4. 作業計画に仕様の中身を書かない。仕様書と要求仕様書に書く
