# 要求の精査

仕様書に反映する前に、バッチ内の要求から曖昧さを取り除く。
依頼者に必ず確認する。確認せずに反映しない。

CLAUDE.md の進め方2「暫定のロジックや暫定の値は依頼者に承認を得る必要がある」を実行する手順。

## 前提

仕様書は書き換えない。書き換えるのは要求仕様書と作業計画だけ。

## 手順

### 1. 曖昧点を洗い出す

対象バッチの REQ 本体を全文読む。以下の形を探す。

| 形 | 例 |
| --- | --- |
| 対応方針が「未定」 | 置き場所が決まっていない |
| 数値が根拠なく置かれている | 閾値3.5、4以上 |
| 「暫定」と書かれている | 判定条件は暫定 |
| 選択肢が併記されたまま | G3に追加、または要件定義工程に追加 |
| アクションアイテムが残っている | 依頼者に提示し承認を得る |

REQ 本体が長い、または複数 REQ にまたがる場合は req-analyst エージェントに洗い出しを任せる。
返ってきた一覧はそのまま使わず、要求仕様書の本文で裏を取る。

### 2. 自分で決められるものを分ける

洗い出した各点を2つに仕分ける。

| 仕分け | 条件 | 扱い |
| --- | --- | --- |
| 自分で決める | CLAUDE.md の設計の前提、または既存の仕様から一意に導ける | 決めて、根拠を対応方針に書く |
| 依頼者に聞く | 値そのものの妥当性。方針の選択。設計の前提に触れる | 確認事項にする |

判断に迷ったら聞く側に倒す。設計の前提9項目に触れるものは必ず聞く。

### 3. 確認する

AskUserQuestion で聞く。最低1問。上限4問。

聞くことが1つもないと判断した場合、それはバッチの選び方が誤っている。req-backlog に戻す。
保留の REQ を扱う以上、承認すべき値か決めるべき方針が必ず存在する。

質問の作り方は以下。

| 項目 | 決まり |
| --- | --- |
| 対象 | 答えが変われば仕様書の書き方が変わるものに限る |
| 選択肢 | 推奨案を先頭に置き、ラベル末尾に「（推奨）」を付ける |
| 説明 | その選択肢を採ったとき仕様書がどうなるかを書く。一般論を書かない |
| 暫定値の承認 | 選択肢に「現行の値のまま確定」を必ず含める |
| 前提の提示 | 質問の前に、現行の記述と暫定である理由を短く示す |

確認事項が4件を超えるバッチは、確認を2回に分ける。1回目の回答が2回目の選択肢を変えるように順序を組む。

### 4. 新しい要求が出たら起票する

確認の過程で依頼者が新しい要望を出すことがある。その場で仕様書に反映しない。
requirement-triage を呼んで REQ-nnn として起票し、作業計画のバッチに載せる。

現在のバッチに入れてよいのは、バッチの上限を超えず、かつ現在の確認事項と同じ性質のものだけ。
それ以外は次以降のバッチに回す。

### 5. 決定を記録する

要求仕様書の該当 REQ を更新する。この時点では仕様書に触れない。

| 欄 | 更新内容 |
| --- | --- |
| 対応方針 | 「未定」を確定内容に書き換える。決めた根拠を1行 |
| アクションアイテム | 済んだ項目を消す。残りがあれば残す |
| 状態 | 保留のまま。仕様書への反映が済んでいないため |

依頼者が現行の暫定値をそのまま承認した場合も、対応方針に「承認日 YYYY-MM-DD」を書く。
承認を得たことが記録に残らないと、次のレビューで同じ確認を繰り返す。

差戻しで P1 に戻ってきた場合は、前回の決定を取り消してから書き直す。上書きで済ませない。

### 6. 作業計画を更新する

対象バッチの確認事項を、決定内容に置き換える。フェーズを P2 にする。

## やらないこと

1. 確認せずに反映へ進まない
2. 自分の推測を仕様書に持ち込まない。確定していないものは REQ にだけ置く
3. 「検討する」で決定を締めない。何が分かれば決まるかを書く
4. 依頼者の回答を要約して記録しない。選んだ選択肢の内容をそのまま残す
5. 確認の場で出た新しい要望を、起票せずに仕様書へ入れない
