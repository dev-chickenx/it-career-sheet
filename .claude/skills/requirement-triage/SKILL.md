# 要求の起票

要求を要求仕様書（docs/01_要求仕様書.md）に登録する。仕様書を直接変更しない。

## 手順

### 1. 要求を切り出す

出所の文書または会話から、要求を1件ずつ切り出す。1文に複数の要求が混ざっていることが多い。

切り出しの粒度は「独立して採否を判断できる単位」とする。
「システムコンサルをジャンルに追加し、守備範囲にも追加する」は2件に分ける。前者を却下しても後者は成立するため。

### 2. 番号を採番する

既存の最大番号の次を使う。番号は再利用しない。

| 範囲 | 出所 |
| --- | --- |
| REQ-001〜099 | 目的から導出 |
| REQ-101〜199 | 打合せ |
| REQ-201〜299 | レビュー |

### 3. 実現性を判定する

| 判定 | 条件 |
| --- | --- |
| 可 | 現在の構造のまま実現できる |
| 条件付き可 | 要求の一部を変える、または別の手段で意図を満たせば実現できる |
| 不可 | 現在の構造では実現できない。構造そのものを変える必要がある |

判定の際は CLAUDE.md の「設計の前提」に照らす。
いずれかに反する要求は「不可」または「条件付き可」になる。

### 4. 難所を書く

なぜ素直に実現できないかを1〜2文で書く。難所がない場合は「なし」と書く。空欄にしない。

難所の典型は以下。

1. 既存の設問と重複する
2. カテゴリの同質性が崩れる
3. 設問数が大きく増える
4. 対応表や判定条件が存在しない
5. 他の要求と衝突する

### 5. 対応方針を書く

実現する場合は、どう実現するかを書く。
実現しない場合は、要求の意図を別の手段でどう満たすかを書く。「見送り」だけで終わらせない。

要求を変更して反映した場合は、状態に「反映済（内容を変更）」と書き、何を変えたかを対応方針に書く。

### 6. 反映先を書く

仕様書の章番号を書く。まだ仕様書に反映していない場合は状態を「保留」にし、反映先を空にする。

## 記載形式

```markdown
### REQ-nnn 要求の要約

| 項目 | 内容 |
| --- | --- |
| 出所 | 目的／議事録（YYYY-MM-DD）／レビュー |
| 要求 | 原文に近い形で1〜2文 |
| 実現性 | 可／条件付き可／不可 |
| 難所 | 素直に実現できない理由 |
| 対応方針 | どう実現するか。しない場合の代替 |
| 反映先 | 仕様書の章番号 |
| 状態 | 反映済／反映済（内容を変更）／保留／見送り |
```

## やらないこと

1. 要求を起票せずに仕様書を変更しない
2. 実現性の判定を飛ばして対応方針を書かない
3. 「検討する」で終わる対応方針を書かない。判断できないなら、何が分かれば判断できるかを書く
