# レビューと締め

反映結果を依頼者が判断できる形で提示し、承認を受けて記録を締める。

提示するのは「要求を実現するために仕様をどう変えたか」である。
変更前と変更後を並べるのは差を見せるためであって、変更前を守るべきものとして扱うためではない。

## 手順

### 1. 反映結果を検査する

提示の前に spec-reviewer エージェントを呼ぶ。差分を執筆基準と設計の前提に照らさせる。
検出があれば直してから提示する。直さずに残すものは、残す理由を提示に含める。

doc-consistency がまだなら先に走らせる。検査を通していないものを依頼者に見せない。

### 2. 提示する

差分をそのまま貼らない。依頼者が判断できる形にする。以下の順で書く。

```markdown
## バッチn の反映結果

### 対応した要求
| REQ | 要求 | 状態 |

### 決めたこと
P1 で確認した事項と、依頼者が選んだ内容。

### 仕様書の変更
| 節 | 変更前 | 変更後 |

### 波及して直した箇所
| 節 | 直した内容 | なぜ連動するか |

### 検査結果
doc-consistency と spec-reviewer の結果。残した検出があればその理由。

### 今回触らなかったこと
このバッチの範囲外だが関連するもの。次のバッチに載っているかを添える。
```

「今回触らなかったこと」を省かない。範囲外だと明示しないと、抜けと受け取られる。

変更前後は、読んで違いが分かる粒度で書く。1文字の差でも意味が変わる箇所は全文を並べる。

### 3. 承認を受ける

依頼者の返答を3つに仕分ける。

| 返答 | 次 |
| --- | --- |
| 承認 | 手順4へ |
| 差戻し | 内容を作業計画に1行で記録し、req-loop の差戻し表に従って戻る |
| 一部承認 | 承認された分だけ締める。差し戻された REQ をバッチから外し、次バッチに回す |

返答が曖昧なときは締めない。承認かどうかを聞き直す。

### 4. 締める

承認された範囲だけを締める。以下を順に行う。

| 対象 | 更新内容 |
| --- | --- |
| 要求仕様書の該当 REQ | 状態を反映済にする。反映先に節番号を書く |
| 要求仕様書6章の一覧 | 締めた REQ の行を消す。一部承認なら状態を書き換える |
| 仕様書1章の版番号 | マイナーを1つ上げる（v1.3 → v1.4） |
| 作業計画 | バッチの状態を反映済にする。承認日を書く |

版番号はマイナーまでとする。パッチは使わない。1バッチを締めるごとに1つ上げる。
変更の大小で上げ幅を変えない。バッチの粒度を版が表す。

版番号を上げたら、仕様書の見出しと本文中の版表記が揃っているかを確認する。

commit は行わない。依頼者が行う。締めの報告に、変更したファイルの一覧を添える。

### 5. 次に渡す

フェーズを P0 にする。req-loop に戻す。

## やらないこと

1. 検査を通す前に提示しない
2. 差分をそのまま貼って判断を委ねない
3. 承認の前に REQ の状態を反映済にしない
4. 一部承認を全部承認として扱わない
5. commit しない。ブランチも切らない
