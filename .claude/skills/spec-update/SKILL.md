# 仕様書への反映

要求仕様書で確定した内容を仕様書に反映する。反映と同時にトレーサビリティを更新する。

## 前提

反映前に、対象の要求が要求仕様書に起票されていることを確認する。
起票されていない場合は requirement-triage を先に実行する。

## 手順

### 1. 現状を読む

仕様書の該当章を読む。相手が編集している可能性があるため、記憶で編集しない。

### 2. 差分編集する

全体上書きをしない。該当箇所だけを編集する。
過去に全体上書きで相手の修正を消した事故が発生している。

### 3. 波及箇所を更新する

設問を変更した場合、以下がすべて連動する。見落としやすい。

| 変更 | 連動して直す箇所 |
| --- | --- |
| カテゴリの追加・削除・改名 | 3.4 アンカー適用表、3.5 識別子、5.3 レーダーの軸数、4.5 意図的な重複 |
| 観点の追加・削除 | 4.6 設問数、4.5 意図的な重複 |
| 工程の観点変更 | 4.6 設問数、5.5 ポジション判定条件 |
| ジャンルの追加・削除 | 3.5 識別子、5.2 マップの行数、5.7 職種対応表 |
| 分析ロジックの変更 | 5章の該当節、8.1 未確定事項 |

### 4. 付録を更新する

| 節 | 更新内容 |
| --- | --- |
| 9.1 | v1 からの変更点に1行追加する |
| 9.2 | 議事録由来の要求の場合、対応状況を更新する |
| 9.3 | 議事録の指示と異なる結論にした場合、理由を書く |

### 5. 要求仕様書を更新する

該当 REQ の「反映先」に章番号を書き、「状態」を反映済にする。

### 6. 数え直す

設問数を変更した場合、4.6 の表を実際に数え直す。前の値からの引き算で済ませない。

```
ブロック1: 18ジャンル × 4スロット
ブロック2: 各工程の観点数の合計
ブロック3: 各カテゴリの観点数の合計
```

## やらないこと

1. 経緯を書かない。「v1ではこうだった」は 9.1 にだけ書く
2. 自明な理由を書かない
3. 未確定のものを断定形で書かない。「未定」と明示し、8.1 に行を作る
